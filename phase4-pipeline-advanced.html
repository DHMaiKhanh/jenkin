Bài 4.1

Multibranch Pipeline

🎯 Mục tiêuHiểu cách Jenkins tự động phát hiện các nhánh/PR có chứa Jenkinsfile và tạo job riêng cho từng nhánh, cấu hình branch source (GitHub), và quản lý vòng đời build cũ.

Multibranch Pipeline là gì?

Một Multibranch Pipeline job quét một repository và tự động tạo một sub-job cho mỗi nhánh (và mỗi Pull Request, nếu bật discovery) có chứa file Jenkinsfile ở gốc. Không cần tạo job thủ công cho từng nhánh mới.

Khái niệmÝ nghĩa
Branch SourceNơi Jenkins quét nhánh: Git, GitHub, Bitbucket, GitLab...
JenkinsfileFile pipeline nằm trong repo — Jenkins tự tìm và chạy.
ScanQuá trình định kỳ quét repo tìm nhánh/PR mới hoặc đã xóa.
Orphaned itemJob của một nhánh đã bị xóa khỏi repo — có thể tự dọn.

Cấu hình Branch Source (GitHub)

Khi tạo job kiểu "Multibranch Pipeline", chọn Branch Sources → GitHub, nhập credentials và repository. Jenkins sẽ:

  • Quét mọi nhánh chứa Jenkinsfile ở đường dẫn cấu hình (mặc định gốc repo).
  • Tùy chọn phát hiện Pull Request (từ origin hoặc từ fork).
  • Chạy lại quét theo lịch (ví dụ mỗi phút, hoặc qua webhook).
Jenkinsfile (đặt ở gốc mỗi nhánh)pipeline {
  agent any
  stages {
    stage('Build') {
      steps { echo "Building branch ${env.BRANCH_NAME}" }
    }
  }
}

Biến môi trường env.BRANCH_NAME luôn có sẵn trong Multibranch Pipeline, giúp phân biệt logic theo nhánh (ví dụ chỉ deploy khi main).

Discard old branch builds

Mục "Discard old items" trong cấu hình Multibranch (hoặc Orphaned Item Strategy) cho phép:

Jenkinsfilepipeline {
  agent any
  options {
    buildDiscarder(logRotator(numToKeepStr: '10'))
  }
  stages {
    stage('Test') { steps { echo 'testing' } }
  }
}
Tùy chọnTác dụng
Days to keep old itemsXóa job của nhánh đã biến mất sau N ngày.
Max # of old items to keepGiới hạn số sub-job/nhánh cũ được giữ lại.

Organization Folders

Organization Folder đi xa hơn một bậc: quét toàn bộ tổ chức/user trên GitHub/Bitbucket và tự động tạo một Multibranch Pipeline job cho mỗi repository có Jenkinsfile. Phù hợp khi một team có hàng chục repo cùng cấu trúc CI.

🤔 Vì sao dùng Multibranch thay vì Freestyle job?Không cần cấu hình build riêng cho từng nhánh/feature branch — pipeline "đi theo code" nhờ nằm trong repo (Pipeline as Code). Tạo nhánh mới, Jenkins tự thấy và build.
⚠️ Lưu ýNếu một nhánh không có Jenkinsfile, Jenkins sẽ không tạo job cho nhánh đó. Webhook cần được cấu hình đúng để tránh chờ quét theo lịch (có thể chậm).
✍️ Thực hànhTạo một Multibranch Pipeline job trỏ tới repo GitHub của bạn, thêm Jenkinsfile vào 2 nhánh khác nhau với thông điệp echo khác nhau, quan sát Jenkins tự tạo 2 sub-job.
📚 5 ví dụ thực tế · Multibranch Pipeline
  1. Jenkinsfile in theo tên nhánh hiện tại. 
    Jenkinsfilepipeline {
  agent any
  stages {
    stage('Info') { steps { echo "Branch: ${env.BRANCH_NAME}" } }
  }
}
  2. Chỉ deploy khi đang ở nhánh main. 
    Jenkinsfilestage('Deploy') {
  when { branch 'main' }
  steps { echo 'Deploying production...' }
}
  3. Giới hạn số build cũ được giữ lại cho mỗi nhánh. 
    Jenkinsfileoptions {
  buildDiscarder(logRotator(numToKeepStr: '5'))
}
  4. Cấu hình đường dẫn Jenkinsfile không nằm ở gốc repo. 
    cấu hình job# Trong "Build Configuration" của Branch Source:
# Script Path: ci/Jenkinsfile
  5. Phân biệt logic build cho Pull Request. 
    Jenkinsfilestage('PR Checks') {
  when { changeRequest() }
  steps { echo 'Running PR validation...' }
}

Lesson 4.1

Multibranch Pipeline

🎯 GoalUnderstand how Jenkins auto-discovers branches/PRs containing a Jenkinsfile and creates a job per branch, configure a branch source (GitHub), and manage the lifecycle of old builds.

What is a Multibranch Pipeline?

A Multibranch Pipeline job scans a repository and automatically creates a sub-job for every branch (and every Pull Request, if discovery is enabled) that contains a Jenkinsfile at its root. No need to manually create a job for each new branch.

ConceptMeaning
Branch SourceWhere Jenkins scans branches from: Git, GitHub, Bitbucket, GitLab...
JenkinsfilePipeline file living in the repo — Jenkins finds and runs it.
ScanPeriodic process that discovers new or deleted branches/PRs.
Orphaned itemA branch's job whose branch was removed from the repo — can be auto-cleaned.

Configuring a Branch Source (GitHub)

When creating a "Multibranch Pipeline" job, choose Branch Sources → GitHub, enter credentials and the repository. Jenkins will:

  • Scan every branch containing a Jenkinsfile at the configured path (repo root by default).
  • Optionally discover Pull Requests (from origin or from forks).
  • Re-scan on a schedule (e.g. every minute, or via webhook).
Jenkinsfile (at the root of each branch)pipeline {
  agent any
  stages {
    stage('Build') {
      steps { echo "Building branch ${env.BRANCH_NAME}" }
    }
  }
}

The env.BRANCH_NAME variable is always available in a Multibranch Pipeline, letting you branch logic (e.g. only deploy on main).

Discarding old branch builds

The "Discard old items" setting (Orphaned Item Strategy) in the Multibranch config lets you:

Jenkinsfilepipeline {
  agent any
  options {
    buildDiscarder(logRotator(numToKeepStr: '10'))
  }
  stages {
    stage('Test') { steps { echo 'testing' } }
  }
}
OptionEffect
Days to keep old itemsDelete a vanished branch's job after N days.
Max # of old items to keepCap how many old branch sub-jobs are retained.

Organization Folders

An Organization Folder goes one level further: it scans an entire GitHub/Bitbucket organization/user and automatically creates a Multibranch Pipeline job for every repository that has a Jenkinsfile. Great when a team owns dozens of repos sharing the same CI structure.

🤔 Why Multibranch instead of a Freestyle job?No need to configure a separate build per branch/feature branch — the pipeline "follows the code" because it lives in the repo (Pipeline as Code). Create a branch, Jenkins sees it and builds automatically.
⚠️ NoteIf a branch has no Jenkinsfile, Jenkins won't create a job for it. Webhooks must be configured correctly to avoid relying on the (potentially slow) scheduled scan.
✍️ ExerciseCreate a Multibranch Pipeline job pointing at your GitHub repo, add a Jenkinsfile to two different branches with different echo messages, and watch Jenkins auto-create two sub-jobs.

  steps { echo 'Deploying production...' }
}
  3. Limit how many old builds are kept per branch.

Shared Libraries

🎯 Mục tiêuHiểu cấu trúc thư mục vars/ và src/, viết một custom step đơn giản, và cách import/dùng thư viện trong nhiều Jenkinsfile khác nhau.

Cấu trúc repository của Shared Library

Một Shared Library là một repo Git riêng với cấu trúc chuẩn:

cây thư mụcmy-shared-lib/
├── vars/                 # mỗi file .groovy = một "global step" gọi trực tiếp
│   └── sayHello.groovy
├── src/                  # class Groovy thông thường (namespace org.foo.Bar)
│   └── org/example/Utils.groovy
└── resources/            # file tĩnh, đọc bằng libraryResource
    └── org/example/template.json
Thư mụcDùng cho
vars/Định nghĩa step gọi được thẳng trong Jenkinsfile, ví dụ sayHello().
src/Class Groovy chuẩn, logic phức tạp, tái sử dụng bởi nhiều step trong vars/.
resources/File không phải code (JSON, template) — nạp bằng libraryResource.

Viết một custom step

vars/sayHello.groovydef call(String name = 'World') {
  echo "Hello, ${name}!"
}

Hàm call() là bắt buộc — nó cho phép gọi file như một hàm. Gọi trong Jenkinsfile khác:

Jenkinsfile@Library('my-shared-lib') _

pipeline {
  agent any
  stages {
    stage('Greet') {
      steps {
        sayHello 'Jenkins'
      }
    }
  }
}

Dòng @Library('my-shared-lib') _ import toàn bộ thư viện; dấu _ là underscore bắt buộc khi không gán biến. Có thể chỉ định phiên bản: @Library('my-shared-lib@v1.2').

Cấu hình Global vs Folder-level Library

Phạm viCấu hình tạiÁp dụng cho
GlobalManage Jenkins → System → Global Pipeline LibrariesMọi pipeline trên toàn instance, không cần approval script.
FolderCấu hình Folder → Pipeline LibrariesChỉ các job nằm trong folder đó — cô lập theo team/project.
🤔 Vì sao cần Shared Library?Nếu 50 repo đều có logic "build Docker image + push registry + gửi Slack" giống nhau, copy-paste vào từng Jenkinsfile là ác mộng bảo trì. Đưa logic đó vào một step dùng chung — sửa một chỗ, mọi pipeline được cập nhật.
⚠️ Sandbox & Script ApprovalCode trong src/ chạy trong Groovy sandbox trừ khi được đánh dấu "trusted" (Global library không sandbox nếu admin cấu hình). Một số API nhạy cảm cần admin approve qua "In-process Script Approval".
✍️ Thực hànhTạo repo my-shared-lib với vars/sayHello.groovy, cấu hình nó làm Global Pipeline Library tên my-shared-lib, rồi gọi từ một Jenkinsfile thử nghiệm.
📚 5 ví dụ thực tế · Shared Libraries
  1. Custom step nhận Map tham số thay vì chuỗi đơn. 
    vars/deployApp.groovydef call(Map config) {
  echo "Deploying ${config.app} to ${config.env}"
}
  2. Gọi step với named parameters trong Jenkinsfile. 
    JenkinsfiledeployApp app: 'checkout-service', env: 'staging'
  3. Class dùng chung trong src/. 
    src/org/example/Notifier.groovypackage org.example
class Notifier implements Serializable {
  static void slack(script, String msg) {
    script.echo "[Slack] ${msg}"
  }
}
  4. Dùng class từ src/ bên trong một step ở vars/. 
    vars/notify.groovyimport org.example.Notifier
def call(String msg) {
  Notifier.slack(this, msg)
}
  5. Import thư viện với phiên bản cụ thể (tag/branch). 
    Jenkinsfile@Library('my-shared-lib@release-2.0') _
pipeline { agent any
  stages { stage('Use') { steps { sayHello() } } }
}
📦 5 bài thực hành · Shared Libraries
  1. Viết custom step vars/printVersion.groovy in ra một chuỗi cố định.
    Đáp án

  echo 'Version 1.0.0'

    Đáp án

    Đáp án

    Đáp án
    @Library('my-shared-lib@v3.1') _
Lesson 4.2

Shared Libraries

🎯 GoalUnderstand the vars/ and src/ folder layout, write a simple custom step, and how to import/use a library across multiple Jenkinsfiles.

Shared Library repository layout

A Shared Library is a dedicated Git repo with a standard structure:

treemy-shared-lib/
├── vars/                 # each .groovy file = a "global step" callable directly
│   └── sayHello.groovy
├── src/                  # regular Groovy classes (namespace org.foo.Bar)
│   └── org/example/Utils.groovy
└── resources/            # static files, read via libraryResource
    └── org/example/template.json
FolderUsed for
vars/Defines steps callable directly in a Jenkinsfile, e.g. sayHello().
src/Standard Groovy classes, complex logic, reused by multiple vars/ steps.
resources/Non-code files (JSON, templates) — loaded via libraryResource.

Writing a custom step

vars/sayHello.groovydef call(String name = 'World') {
  echo "Hello, ${name}!"
}

The call() method is required — it lets the file be invoked like a function. Calling it from another Jenkinsfile:

Jenkinsfile@Library('my-shared-lib') _

pipeline {
  agent any
  stages {
    stage('Greet') {
      steps {
        sayHello 'Jenkins'
      }
    }
  }
}

The @Library('my-shared-lib') _ line imports the whole library; the trailing _ underscore is required when not assigning to a variable. A version can be pinned: @Library('my-shared-lib@v1.2').

Global vs folder-level library configuration

ScopeConfigured atApplies to
GlobalManage Jenkins → System → Global Pipeline LibrariesEvery pipeline on the whole instance, no need for script approval.
FolderFolder configuration → Pipeline LibrariesOnly jobs inside that folder — isolated per team/project.
🤔 Why use a Shared Library?If 50 repos all share the same "build Docker image + push registry + notify Slack" logic, copy-pasting it into every Jenkinsfile is a maintenance nightmare. Move that logic into a shared step — fix it once, every pipeline gets the update.
⚠️ Sandbox & Script ApprovalCode in src/ runs inside the Groovy sandbox unless marked "trusted" (a Global library can be unsandboxed if the admin configures it). Some sensitive APIs require an admin to approve via "In-process Script Approval".
✍️ ExerciseCreate a my-shared-lib repo with vars/sayHello.groovy, configure it as a Global Pipeline Library named my-shared-lib, then call it from a test Jenkinsfile.

}
  2. Call the step with named parameters in a Jenkinsfile.

  3. A shared class inside src/. 
    src/org/example/Notifier.groovypackage org.example

  4. Using the src/ class from a step in vars/.

  5. Import the library pinned to a specific version (tag/branch).

Bài 4.3

Parallel & Matrix

🎯 Mục tiêuChạy nhiều nhánh công việc song song với parallel {}, dừng sớm bằng failFast, và nhân bản một stage theo nhiều tổ hợp biến với matrix {}.

Parallel trong một stage

Khối parallel declarative cho phép chạy nhiều nhánh con đồng thời, mỗi nhánh có thể chạy trên agent khác nhau.

Jenkinsfilepipeline {
  agent none
  stages {
    stage('Test') {
      failFast true
      parallel {
        stage('Unit') {
          agent any
          steps { sh 'npm run test:unit' }
        }
        stage('Lint') {
          agent any
          steps { sh 'npm run lint' }
        }
        stage('E2E') {
          agent any
          steps { sh 'npm run test:e2e' }
        }
      }
    }
  }
}
Tùy chọnÝ nghĩa
failFast trueHủy các nhánh song song còn lại ngay khi một nhánh fail.
agent any trong mỗi nhánhCho phép mỗi nhánh chạy trên executor/agent riêng, thật sự song song.
💡 parallelsAlwaysFailFast()Có thể đặt trong khối options {} cấp pipeline để áp dụng failFast cho mọi khối parallel mà không cần khai báo lại từng chỗ.

Matrix — nhân bản stage theo trục

matrix {} tự động tạo tổ hợp Cartesian của các axes, chạy một bản sao stage cho mỗi tổ hợp — lý tưởng cho build đa hệ điều hành/đa trình duyệt.

Jenkinsfilepipeline {
  agent none
  stages {
    stage('Cross-browser tests') {
      matrix {
        axes {
          axis {
            name 'BROWSER'
            values 'chrome', 'firefox', 'safari'
          }
          axis {
            name 'OS'
            values 'linux', 'windows'
          }
        }
        excludes {
          exclude {
            axis { name 'BROWSER'; values 'safari' }
            axis { name 'OS'; values 'windows' }
          }
        }
        stages {
          stage('Run') {
            agent any
            steps { sh "run-tests --browser=${BROWSER} --os=${OS}" }
          }
        }
      }
    }
  }
}
Phần tửVai trò
axes / axisMỗi axis là một biến với danh sách giá trị; matrix nhân tổ hợp tất cả các axis.
excludesLoại bỏ những tổ hợp không hợp lệ/không cần chạy (ví dụ Safari trên Windows).
stages bên trong matrixCác stage này lặp lại cho mỗi "cell" (tổ hợp) còn lại sau khi loại trừ.
🤔 Khi nào dùng matrix thay vì viết tay nhiều stage?Khi số tổ hợp lớn (3 browser × 2 OS = 6), viết tay 6 stage riêng biệt cực kỳ lặp lại và khó bảo trì. Matrix sinh chúng tự động chỉ từ khai báo axes.
⚠️ Lưu ýMỗi cell trong matrix chạy trên agent/executor riêng — cần đủ agent khả dụng, nếu không các cell sẽ xếp hàng chờ. agent none ở cấp pipeline là bắt buộc khi dùng parallel/matrix để tránh khóa một agent không cần thiết ở cấp cao nhất.
✍️ Thực hànhViết một pipeline có stage "Test" chạy song song 2 nhánh Unit và Lint với failFast true, sau đó thêm một stage matrix chạy trên 2 giá trị NODE_VERSION (16, 18).
📚 5 ví dụ thực tế · Parallel & Matrix
  1. Chạy song song build frontend và backend. 
    Jenkinsfilestage('Build') {
  parallel {
    stage('Frontend') { agent any; steps { sh 'npm run build' } }
    stage('Backend')  { agent any; steps { sh './gradlew build' } }
  }
}
  2. Bật failFast để dừng ngay khi một nhánh lỗi. 
    Jenkinsfilestage('Test') {
  failFast true
  parallel { stage('A') { steps { sh './a.sh' } } stage('B') { steps { sh './b.sh' } } }
}
  3. Matrix build với một trục duy nhất (nhiều phiên bản Node). 
    Jenkinsfilematrix {
  axes { axis { name 'NODE'; values '16', '18', '20' } }
  stages { stage('Test') { steps { sh "nvm use ${NODE} && npm test" } } }
}
  4. Matrix 2 trục cho OS và kiến trúc CPU. 
    Jenkinsfileaxes {
  axis { name 'OS';   values 'linux', 'mac' }
  axis { name 'ARCH'; values 'amd64', 'arm64' }
}
  5. Áp dụng failFast toàn cục cho mọi khối parallel. 
    Jenkinsfileoptions {
  parallelsAlwaysFailFast()
}
📦 5 bài thực hành · Parallel & Matrix
  1. Viết một khối parallel với 2 nhánh A và B.
    Đáp án
    parallel {
  stage('A') { steps { echo 'A' } }

Lesson 4.3

Parallel & Matrix

🎯 GoalRun multiple branches of work concurrently with parallel {}, fail fast with failFast, and replicate a stage across combinations of variables with matrix {}.

Parallel inside a stage

The declarative parallel block runs several sub-branches concurrently, each of which may run on a different agent.

Jenkinsfilepipeline {
  agent none
  stages {
    stage('Test') {
      failFast true
      parallel {
        stage('Unit') {
          agent any
          steps { sh 'npm run test:unit' }
        }
        stage('Lint') {
          agent any
          steps { sh 'npm run lint' }
        }
        stage('E2E') {
          agent any
          steps { sh 'npm run test:e2e' }
        }
      }
    }
  }
}
OptionMeaning
failFast trueCancel remaining parallel branches as soon as one fails.
agent any per branchLets each branch run on its own executor/agent, truly in parallel.
💡 parallelsAlwaysFailFast()Can be placed in the pipeline-level options {} block to apply failFast to every parallel block without repeating it everywhere.

Matrix — replicating a stage across axes

matrix {} automatically generates the Cartesian product of the given axes, running a copy of the stage for every combination — ideal for cross-OS/cross-browser builds.

Jenkinsfilepipeline {
  agent none
  stages {
    stage('Cross-browser tests') {
      matrix {
        axes {
          axis {
            name 'BROWSER'
            values 'chrome', 'firefox', 'safari'
          }
          axis {
            name 'OS'
            values 'linux', 'windows'
          }
        }
        excludes {
          exclude {
            axis { name 'BROWSER'; values 'safari' }
            axis { name 'OS'; values 'windows' }
          }
        }
        stages {
          stage('Run') {
            agent any
            steps { sh "run-tests --browser=${BROWSER} --os=${OS}" }
          }
        }
      }
    }
  }
}
ElementRole
axes / axisEach axis is a variable with a list of values; matrix multiplies all axes together.
excludesRemoves combinations that are invalid/unnecessary (e.g. Safari on Windows).
stages inside matrixThese stages repeat for every remaining "cell" (combination) after exclusion.
🤔 When to use matrix instead of hand-writing stages?When the number of combinations is large (3 browsers × 2 OSes = 6), hand-writing 6 separate stages is repetitive and hard to maintain. Matrix generates them automatically from the axes declaration.
⚠️ NoteEach matrix cell runs on its own agent/executor — you need enough agents available, otherwise cells queue up. agent none at the pipeline level is required when using parallel/matrix to avoid needlessly locking an agent at the top level.
✍️ ExerciseWrite a pipeline with a "Test" stage that runs Unit and Lint branches in parallel with failFast true, then add a matrix stage running against two NODE_VERSION values (16, 18).

Điều kiện when

🎯 Mục tiêuChạy hoặc bỏ qua một stage tùy theo điều kiện: nhánh, biến môi trường, biểu thức Groovy, thay đổi file, và kết hợp nhiều điều kiện với allOf/anyOf.

Điều kiện cơ bản

Jenkinsfilestage('Deploy') {
  when { branch 'main' }
  steps { sh './deploy.sh' }
}
Điều kiệnKiểm tra
branch 'main'Tên nhánh hiện tại (chỉ Multibranch Pipeline).
environment name: 'DEPLOY', value: 'true'Giá trị của một biến môi trường.
expression { ... }Biểu thức Groovy tùy ý, trả về true/false.
changeset "**/*.js"Có file khớp pattern bị thay đổi trong commit.
tag "release-*"Build được kích hoạt từ một Git tag khớp pattern.

expression{} — logic Groovy tùy ý

Jenkinsfilestage('Nightly only') {
  when {
    expression { return params.RUN_NIGHTLY == true }
  }
  steps { sh './nightly-tests.sh' }
}

Kết hợp nhiều điều kiện

Jenkinsfilestage('Deploy prod') {
  when {
    allOf {
      branch 'main'
      environment name: 'DEPLOY_ENV', value: 'prod'
    }
  }
  steps { sh './deploy-prod.sh' }
}

stage('Notify') {
  when {
    anyOf {
      branch 'main'
      branch 'release/*'
    }
  }
  steps { sh './notify.sh' }
}
CombinatorÝ nghĩa
allOf { ... }Tất cả điều kiện con phải đúng (AND).
anyOf { ... }Chỉ cần một điều kiện con đúng (OR).
not { ... }Phủ định một điều kiện.

changeset — chỉ chạy khi file liên quan thay đổi

Jenkinsfilestage('Frontend tests') {
  when { changeset "frontend/**" }
  steps { sh 'npm test' }
}
💡 beforeAgent trueĐặt when { beforeAgent true; branch 'main' } để Jenkins kiểm tra điều kiện trước khi cấp phát agent cho stage — tiết kiệm tài nguyên khi điều kiện false.
🤔 Vì sao when tốt hơn if/else trong script?when là cú pháp declarative chuẩn, được Jenkins hiển thị rõ ràng trên UI (stage bị skip có nhãn riêng), dễ đọc hơn so với việc nhồi logic điều kiện vào một pipeline kiểu Scripted.
⚠️ Lưu ýchangeset so khớp theo Ant-style glob và phụ thuộc vào SCM plugin hỗ trợ (Git hỗ trợ tốt). Với multibranch, một số điều kiện như branch chỉ có ý nghĩa khi job thực sự là Multibranch/Organization Folder.
✍️ Thực hànhViết pipeline với 3 stage: "Test" luôn chạy, "Deploy Staging" chỉ khi nhánh là develop, "Deploy Prod" chỉ khi nhánh main VÀ biến APPROVED=true.

When Conditions

🎯 GoalRun or skip a stage based on conditions: branch, environment variable, Groovy expression, changed files, and combining conditions with allOf/anyOf.

Basic conditions

Jenkinsfilestage('Deploy') {
  when { branch 'main' }
  steps { sh './deploy.sh' }
}
ConditionChecks
branch 'main'Current branch name (Multibranch Pipeline only).
environment name: 'DEPLOY', value: 'true'The value of an environment variable.
expression { ... }Arbitrary Groovy expression returning true/false.
changeset "**/*.js"Whether a file matching the pattern was changed in the commit.
tag "release-*"Build was triggered from a Git tag matching the pattern.

expression{} — arbitrary Groovy logic

Jenkinsfilestage('Nightly only') {
  when {
    expression { return params.RUN_NIGHTLY == true }
  }
  steps { sh './nightly-tests.sh' }
}

Combining multiple conditions

Jenkinsfilestage('Deploy prod') {
  when {
    allOf {
      branch 'main'
      environment name: 'DEPLOY_ENV', value: 'prod'
    }
  }
  steps { sh './deploy-prod.sh' }
}

stage('Notify') {
  when {
    anyOf {
      branch 'main'
      branch 'release/*'
    }
  }
  steps { sh './notify.sh' }
}
CombinatorMeaning
allOf { ... }All nested conditions must be true (AND).
anyOf { ... }Only one nested condition needs to be true (OR).
not { ... }Negates a condition.

Jenkinsfilestage('Frontend tests') {
  when { changeset "frontend/**" }
  steps { sh 'npm test' }
}

🤔 Why is when better than script if/else?when is standard declarative syntax, clearly surfaced in the Jenkins UI (a skipped stage gets its own label), and easier to read than embedding conditional logic in a Scripted-style pipeline.
⚠️ Notechangeset matches Ant-style globs and depends on SCM plugin support (Git supports it well). In multibranch, conditions like branch only make sense when the job is actually a Multibranch/Organization Folder job.

🎯 Mục tiêuKhai báo tham số build với parameters {} (string/choice/booleanParam), tạo cổng phê duyệt thủ công với input, giới hạn người phê duyệt bằng submitter, và kết hợp với timeout.

Khối parameters

Jenkinsfilepipeline {
  agent any
  parameters {
    string(name: 'VERSION', defaultValue: '1.0.0', description: 'Phiên bản cần deploy')
    choice(name: 'ENVIRONMENT', choices: ['staging', 'production'], description: 'Môi trường đích')
    booleanParam(name: 'RUN_TESTS', defaultValue: true, description: 'Có chạy test không')

    stage('Deploy') {

    }
  }
}

stringNhập chuỗi tự do (version, tên nhánh, ticket ID...).
choiceChọn một trong danh sách cố định (môi trường, region...).
booleanParamBật/tắt một hành vi (chạy test, skip cache...).

Truy cập giá trị tham số trong pipeline qua biến params.TÊN_THAM_SỐ.

input — cổng phê duyệt thủ công

Jenkinsfilestage('Approve production deploy') {

    }

okNhãn nút xác nhận.

Kết hợp input với timeout

Nếu không ai phê duyệt, pipeline sẽ treo agent vô thời hạn (hoặc chiếm executor nếu input chạy trong stage có agent). Bọc trong timeout để tự hủy sau một khoảng thời gian:

Jenkinsfilestage('Approve production deploy') {

    }

}

  steps { sh './deploy-prod.sh' }
}
💡 Best practiceĐặt stage input với agent none/không giữ workspace (dùng options { skipDefaultCheckout() } hoặc tách stage input khỏi stage cần agent) để không chiếm executor trong lúc chờ người duyệt.

⚠️ Lưu ý bảo mậtKhông đặt submitter nghĩa là bất kỳ ai có quyền Job/Build đều phê duyệt được. Luôn khai báo submitter cho các bước nhạy cảm như deploy production.

🎯 GoalDeclare build parameters with parameters {} (string/choice/booleanParam), create a manual approval gate with input, restrict approvers with submitter, and combine it with timeout.

The parameters block

Jenkinsfilepipeline {
  agent any
  parameters {
    string(name: 'VERSION', defaultValue: '1.0.0', description: 'Version to deploy')
    choice(name: 'ENVIRONMENT', choices: ['staging', 'production'], description: 'Target environment')
    booleanParam(name: 'RUN_TESTS', defaultValue: true, description: 'Whether to run tests')

  }
}
Parameter typeUse when
stringFree-form text input (version, branch name, ticket ID...).
choicePick one of a fixed list (environment, region...).
booleanParamToggle a behavior on/off (run tests, skip cache...).

Access parameter values in the pipeline via params.PARAMETER_NAME.

input — a manual approval gate

Jenkinsfilestage('Approve production deploy') {
  steps {
    script {
      input message: 'Deploy to production?',
            ok: 'Deploy',
            submitter: 'release-managers'
    }
  }
}
input parameterMeaning
messageText shown to the approver.
okLabel of the confirm button.
submitterOnly the listed user/group is allowed to approve.
parametersCan request additional parameter input at the same step.

Combining input with timeout

If nobody approves, the pipeline will hang indefinitely (or hold an executor if input runs inside a stage with an agent). Wrap it in timeout to auto-abort after a period:

Jenkinsfilestage('Approve production deploy') {
  steps {
    timeout(time: 15, unit: 'MINUTES') {
      input message: 'Deploy to production?', submitter: 'release-managers'
    }
  }
}
stage('Deploy') {
  steps { sh './deploy-prod.sh' }
}
💡 Best practiceGive the input stage agent none/avoid holding a workspace (use options { skipDefaultCheckout() } or separate the input stage from the stage needing an agent) so it doesn't occupy an executor while waiting for approval.
🤔 Why input instead of a manual trigger?input lets a pipeline pause at exactly the right moment — the build has already run tests/built, and only a human decision is missing before deploy — instead of having to manually re-run the whole job.
⚠️ Security noteOmitting submitter means anyone with Job/Build permission can approve. Always declare submitter for sensitive steps like production deploys.
