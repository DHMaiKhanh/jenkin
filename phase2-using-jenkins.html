Bài 2.1

Freestyle Project

🎯 Mục tiêuTạo được một Freestyle job từ đầu đến cuối: lấy code từ SCM, chuẩn bị môi trường build, chạy build step, và lưu lại kết quả (artifact) sau khi build xong.

Freestyle project là gì?

Freestyle project là loại job cổ điển, đa năng, cấu hình hoàn toàn bằng giao diện web (click chuột, điền form) — không cần viết code. Đây là loại job đầu tiên và dễ học nhất của Jenkins, rất hợp cho người mới.

📖 Đọc mô tả gốc trên màn hình chọn loại job"Classic, general-purpose job type that checks out from up to one SCM, executes build steps serially, followed by post-build steps..." → Loại job kinh điển, đa dụng — checkout từ tối đa 1 nguồn code (SCM), chạy các bước build tuần tự (lần lượt), sau đó chạy các bước post-build như archive artifact và gửi email.
🧠 Đặc điểm cần nhớ
  • ✅ Không cần code — chỉ click và điền form → dễ cho người mới.
  • ➡️ Chạy tuần tự (serial) — các Build Steps chạy lần lượt từ trên xuống, không song song.
  • 🔗 Tối đa 1 SCM — chỉ checkout được từ 1 repo.
  • 💾 Cấu hình lưu trong config.xml trên server, không nằm trong Git → khó review, khó backup bằng version control.

Lesson 2.1

Freestyle Projects

🎯 GoalBuild a Freestyle job from start to finish: pull code from SCM, prepare the build environment, run build steps, and preserve results (artifacts) after the build finishes.

What is a Freestyle project?

A Freestyle project is the classic, general-purpose job type, configured entirely through the web UI (clicking and filling in forms) — no code required. It's Jenkins' first and easiest job type to learn, ideal for beginners.

📖 Reading the original description on the job-type picker"Classic, general-purpose job type that checks out from up to one SCM, executes build steps serially, followed by post-build steps..." → a classic, all-purpose job that checks out from at most one SCM, runs build steps serially (one after another), then runs post-build steps like archiving artifacts and sending email.
🧠 Key things to remember
  • ✅ No code needed — just click and fill in forms → beginner-friendly.
  • ➡️ Runs serially — Build Steps run top to bottom in order, never in parallel.
  • 🔗 At most one SCM — checks out from a single repo only.
  • 💾 Config lives in config.xml on the server, not in Git → harder to review and to back up via version control.

👉 Bottom lineFor the "Hello Jenkins" exercise, Freestyle is the right choice — simple, visual, no code. Only when a real project grows multiple steps (build → test → deploy) do people move to Pipeline.

Post-build Actions

After Build Steps finish (success or failure), Jenkins runs the configured Post-build Actions. The most common is Archive the artifacts — saving build outputs (jars, zips, reports...) for later download, even after the workspace is wiped on the next build.

Bài 2.2

Build Triggers

🎯 Mục tiêuBiết cách cho job tự động chạy: theo lịch, theo thay đổi SCM, khi có project khác chạy xong, hoặc gọi từ xa qua API token.

Poll SCM

Jenkins định kỳ kiểm tra repository xem có commit mới không (không cần webhook). Cấu hình bằng cú pháp cron 5 trường: MINUTE HOUR DOM MONTH DOW.

Build Triggers → Poll SCM# Kiểm tra mỗi 5 phút
H/5 * * * *
# Kiểm tra mỗi giờ, phút do Jenkins tự "hash" để rải tải
H * * * *
💡 Ký tự H là gì?H (hash) thay cho một số cố định, được Jenkins băm theo tên job để rải đều thời điểm chạy giữa nhiều job — tránh tất cả job cùng poll vào đúng phút 0.

Đào sâu: cú pháp cron 5 trường & ký tự H

Jenkins dùng cron 5 trường. Mỗi trường điều khiển một chiều thời gian, cách nhau bởi khoảng trắng:

Cấu trúc cron Jenkins┌───────────── phút (0-59)
│ ┌───────────── giờ (0-23)
│ │ ┌───────────── ngày trong tháng (1-31)
│ │ │ ┌───────────── tháng (1-12)
│ │ │ │ ┌───────────── thứ trong tuần (0-7, 0 và 7 = Chủ nhật)
│ │ │ │ │
* * * * *

Vấn đề mà H giải quyết: nếu 1000 job đều đặt 0 2 * * * (2h sáng), tất cả nổ cùng lúc lúc 2:00:00 → Jenkins nghẽn, Git server bị 1000 request đồng thời. H bảo Jenkins tự chọn một giá trị cố định dựa trên tên job: mỗi job ra một phút khác nhau (rải đều tải) nhưng ổn định — cùng job luôn chạy đúng phút đó.

Ví dụ với H# ~2h sáng — Jenkins chọn phút cụ thể, vd 2:37
H 2 * * *
# mỗi 5 phút nhưng lệch pha (vd :02, :07, :12...)
H/5 * * * *
# hash trong khoảng phút 0-29
H(0-29) * * * *
# ~10h tối, thứ 2 đến thứ 6
H 22 * * 1-5
👉 Quy tắc vàngGần như luôn dùng H thay cho số cố định ở trường phút, trừ khi bạn thật sự cần chạy đúng giây phút đó.

Poll SCM hoạt động bên trong ra sao?

Cứ mỗi chu kỳ (vd 5 phút với H/5 * * * *), Jenkins làm:

  1. Chạy git ls-remote / git fetch để lấy commit hash mới nhất trên remote.
  2. So sánh với hash của lần build trước.
  3. Khác nhau → trigger build. Giống nhau → không làm gì.
🧠 Điểm dễ nhầmPoll SCM không clone toàn bộ repo mỗi lần — nó chỉ hỏi "hash mới nhất là gì?". Nhưng vẫn tốn: một tiến trình poll trên Jenkins + một request tới Git server mỗi chu kỳ, kể cả khi 3 tuần không ai commit. Và độ trễ = chu kỳ cron: commit lúc 10:01 nhưng poll lúc 10:05 → build trễ 4 phút.

Webhook — GitHub hook trigger

Thay vì poll định kỳ (có độ trễ, tốn tài nguyên), GitHub/GitLab có thể gọi thẳng vào Jenkins ngay khi có push, qua endpoint /github-webhook/. Bật "GitHub hook trigger for GITScm polling" trong Build Triggers, và cấu hình webhook phía GitHub trỏ về Jenkins.

GitHub → Settings → WebhooksPayload URL: https://jenkins.example.com/github-webhook/
Content type: application/json
Events: Just the push event

Khác biệt cốt lõi là chiều gọi: Poll SCM là Jenkins kéo (pull) lặp lại, webhook là GitHub đẩy (push) khi có sự kiện.

🧠 Tinh tế: webhook không trực tiếp buildCheckbox tên là "GitHub hook trigger for GITScm polling" — khi GitHub POST tới /github-webhook/, Jenkins chỉ chạy một lần poll ngay lập tức, thấy commit mới rồi mới build. Vì thế job vẫn cần bật Git SCM. Nếu Jenkins nằm sau firewall, GitHub không gọi vào được → buộc phải dùng Poll SCM.

🎯 GoalLearn how to make a job run automatically: on a schedule, on SCM changes, after another project finishes, or remotely via an API token.

Poll SCM

Jenkins periodically checks the repository for new commits (no webhook needed). Configured with a 5-field cron syntax: MINUTE HOUR DOM MONTH DOW.

Build Triggers → Poll SCM# Check every 5 minutes
H/5 * * * *
# Check hourly, minute hashed by Jenkins to spread the load
H * * * *
💡 What does the H mean?H (hash) stands in for a fixed number, hashed by Jenkins from the job name to spread execution times across many jobs — avoiding every job polling at minute 0 simultaneously.

Deeper: the 5-field cron syntax & the H character

Jenkins uses 5 fields, each controlling one axis of time, separated by spaces:

Jenkins cron layout┌───────────── minute (0-59)
│ ┌───────────── hour (0-23)
│ │ ┌───────────── day of month (1-31)
│ │ │ ┌───────────── month (1-12)
│ │ │ │ ┌───────────── day of week (0-7, 0 and 7 = Sunday)
│ │ │ │ │
* * * * *

The problem H solves: if 1000 jobs all set 0 2 * * * (2am), they all fire at exactly 2:00:00 → Jenkins stalls, the Git server takes 1000 simultaneous requests. H tells Jenkins to pick a fixed value from the job name: each job lands on a different minute (load spread out) yet is stable — the same job always runs at that minute.

Examples with H# ~2am — Jenkins picks a concrete minute, e.g. 2:37
H 2 * * *
# every 5 minutes but phase-shifted (e.g. :02, :07, :12...)
H/5 * * * *
# hash within the 0-29 minute range
H(0-29) * * * *
# ~10pm, Monday to Friday
H 22 * * 1-5
👉 Golden ruleAlmost always use H instead of a fixed number in the minute field, unless you truly need it to run at an exact minute.

How does Poll SCM work internally?

Every cycle (e.g. 5 minutes with H/5 * * * *), Jenkins:

  1. Runs git ls-remote / git fetch to get the latest commit hash on the remote.
  2. Compares it with the hash from the previous build.
  3. Different → trigger a build. Same → do nothing.
🧠 Easy to get wrongPoll SCM does not clone the whole repo each time — it just asks "what's the latest hash?". But it still costs one poll process on Jenkins + one request to the Git server every cycle, even after three weeks with no commits. And latency = the cron interval: a commit at 10:01 with a poll at 10:05 means the build is 4 minutes late.

Webhook — GitHub hook trigger

Instead of periodic polling (adds delay, wastes resources), GitHub/GitLab can call Jenkins directly on push via the /github-webhook/ endpoint. Enable "GitHub hook trigger for GITScm polling" under Build Triggers, and configure a webhook on the GitHub side pointing at Jenkins.

GitHub → Settings → WebhooksPayload URL: https://jenkins.example.com/github-webhook/
Content type: application/json
Events: Just the push event
MechanismLatencyRequirement
Poll SCMCron interval (minutes)Jenkins need not be publicly reachable
WebhookNearly instantJenkins must have a URL reachable from GitHub

The core difference is the direction of the call: Poll SCM is Jenkins pulling repeatedly; a webhook is GitHub pushing when an event happens.

Pull vs PushPoll SCM (pull):   Jenkins  ──"anything new?"──►  GitHub   (repeats forever)
Webhook  (push):   GitHub   ──"just got a push!"──►  Jenkins  (only on an event)
🧠 Subtlety: the webhook doesn't build directlyThe checkbox is named "GitHub hook trigger for GITScm polling" — when GitHub POSTs to /github-webhook/, Jenkins just runs a single poll immediately, sees the new commit, and then builds. So the job still needs Git SCM enabled. If Jenkins sits behind a firewall, GitHub can't reach it → you're forced to use Poll SCM.

Build periodically & Trigger remotely

Build periodically uses the same cron syntax but runs the job regardless of SCM changes — good for cleanup jobs, periodic reports, nightly builds.

Same cron syntax, completely different logic from Poll SCM — this is a common mix-up:

TriggerWhen the time comes...

Use Build periodically for: nightly builds, cleaning old artifacts, periodic reports, health checks — anything that must run on a fixed cadence regardless of commits.

Credential dùng để làm gì?

Credential là nơi lưu trữ tập trung và bảo mật các thông tin nhạy cảm mà Jenkins cần để kết nối tới hệ thống bên ngoài. Thay vì hard-code mật khẩu/token vào pipeline hay job config, bạn lưu vào Credentials Store rồi tham chiếu qua một ID.

Lợi ích bảo mật

  • Mã hóa khi lưu trữ — Jenkins mã hóa credential, không lưu dạng plain text.
  • Ẩn trong log — giá trị secret bị che thành **** trong console output.
  • Phân quyền — kiểm soát job/người dùng nào được dùng credential nào (scope Global vs Folder-level).
  • Dễ thay đổi — đổi mật khẩu ở một chỗ, mọi job dùng chung đều được cập nhật.

Scope: Global vs System vs Domain

Credentials

🎯 GoalUnderstand the credential types in Jenkins, their storage scope, and the two ways to use a credential in a job: picking it in the UI vs referencing it by ID in script/Pipeline.

What are credentials for?

Credentials are the central, secure store for the sensitive information Jenkins needs to connect to external systems. Instead of hard-coding passwords/tokens into a pipeline or job config, you save them in the Credentials Store and reference them by an ID.

PurposeReal-world example
Connect to a Git repositoryClone code from a private GitHub/GitLab/Bitbucket repo
Access a deploy serverSSH key to deploy code to production/staging servers
Log into a Docker RegistryPush/pull images from Docker Hub, Harbor, ECR…
Call external APIsTokens to integrate Slack, SonarQube, AWS, Kubernetes…
Connect to a DatabaseUsername/password when running migrations or tests

Security benefits

  • Encrypted at rest — Jenkins encrypts credentials; they are never stored as plain text.
  • Masked in logs — secret values are hidden as **** in the console output.
  • Access control — control which jobs/users can use which credential (Global vs Folder-level scope).
  • Easy to rotate — change a password in one place and every job that shares it is updated.

Credential types

TypeUsed for
Username with passwordGit over HTTP, Docker registry login, any user/pass API
SSH Username with private keyGit over SSH, connecting agents over SSH
Secret textA single secret string (API key, token)
Secret fileA secret file (kubeconfig, .p12, service account JSON)
CertificateA client certificate (.pfx/.p12) with its password

Access via: Manage Jenkins → Credentials → System → Global credentials (unrestricted) → Add Credentials.

Scope: Global vs System vs Domain

  • Global — usable by any job, node, or Pipeline. The most common.
  • System — used only by Jenkins core itself (e.g. email server or LDAP credentials); not exposed to jobs.
  • Domain — a credential store can be split into multiple "domains" scoped by host/URL conditions, so Jenkins auto-selects the right credential when several of the same type exist.
🤔 Why does System scope exist separately?Some credentials (e.g. an SMTP password used to send alert emails) are only needed by Jenkins' own infrastructure and shouldn't be visible or selectable by every job — narrowing the scope reduces leak risk.

Using credentials in a Freestyle job vs referencing by ID

In Freestyle, you pick a credential from a dropdown in Source Code Management or a build step (e.g. the SSH Agent plugin) — Jenkins injects the value automatically at build time.

Freestyle → Source Code ManagementCredentials: (dropdown) → github-token

In Pipeline/scripts, you reference the ID assigned when the credential was created, and never hard-code the real value:

Jenkinsfile (scripted binding)withCredentials([string(credentialsId: 'github-token', variable: 'TOKEN')]) {
  sh 'curl -H "Authorization: token $TOKEN" https://api.github.com/user'
}
💡 The ID is a stable contractGive it a clear, memorable ID (github-token, docker-hub-creds) because the Pipeline references that exact string — changing the ID without updating the Jenkinsfile breaks the build.
⚠️ Never echo a credential value into the logJenkins auto-masks secret values only when you use the proper withCredentials/credential binding mechanism. If you assign an env var another way or run echo $TOKEN, the value can leak straight into the Console Output.

Lesson 2.6 · Case study

Upgrading Jenkins safely — a real lessons-learned

🎯 GoalRead the Manage Jenkins banners, tell a critical warning apart from an informational one, and run a safe WAR upgrade (backup → download → stop → replace → verify) with a clean rollback path. Recorded from a real upgrade: 2.568.1 → 2.568.2 on 2026-08-06.

Context: what is Manage Jenkins reporting?

Opening Manage Jenkins shows a stack of warning banners. Here is the actual situation:

🤵 Jenkins / Manage Jenkins
⛔It appears that your reverse proxy set up is broken.More Info
ℹ️New version of Jenkins (2.568.2) is available for download (changelog).Or Upgrade Automatically
⚠️Building on the built-in node can be a security issue. You should set up distributed builds.Set up agent
⛔Warnings have been published for the following currently installed components:
Jenkins 2.568.1 core and libraries: Multiple security vulnerabilities in Jenkins 2.575 and earlier, LTS 2.568.1 and earlier. A fix for this issue is available. Update Jenkins now.View
ℹ️Jenkins can enforce Content Security Policy (CSP)… CSP is disabled by default but recommended, if possible.Learn more

Figure 2.6 — Manage Jenkins page (before upgrade), reproduced in HTML/CSS.

Not every banner is dangerous. By severity:

BannerSeverityAction
🔴 Security vulnerabilities — "A fix is available"CriticalUpgrade Jenkins now (the main reason to act)
🔴 Reverse proxy set up is brokenMediumUsually a wrong Jenkins URL port — make it match the real URL
🟡 Building on the built-in nodeShould fixSet up a dedicated agent to isolate builds from the controller (not urgent)
🔵 New version availableInfoSame thing as the security fix above
🔵 Content Security Policy (CSP)SuggestionOptional, hardens against XSS
🤔 Why does "reverse proxy broken" appear with no proxy?This host runs java -jar jenkins.war --httpPort=9090 directly, no nginx/Apache. The banner fires because the configured Jenkins URL is http://localhost:8080/ while access is actually via :9090 — Jenkins compares the configured URL to the real request, sees a mismatch, and complains. Making the URL match clears it.

The safe WAR upgrade procedure (as performed)

System profile: runs java -jar jenkins.war --httpPort=9090, war at C:\Users\MAI KHANH\jenkins.war, JENKINS_HOME = C:\Users\MAI KHANH\.jenkins, Temurin Java 21.

  1. Back up JENKINS_HOME and the old war first — this is your rollback path. 
    PowerShell — backup# Back up the whole JENKINS_HOME + old war
Copy-Item "C:\Users\MAI KHANH\.jenkins" "C:\Users\MAI KHANH\.jenkins_backup_2026-08-06" -Recurse
Copy-Item "C:\Users\MAI KHANH\jenkins.war" "C:\Users\MAI KHANH\jenkins-2.568.1.war.bak"
  2. Download the new 2.568.2 (LTS) — while Jenkins is still up, to minimize downtime. 
    PowerShell — downloadInvoke-WebRequest -Uri "https://get.jenkins.io/war-stable/2.568.2/jenkins.war" `
  -OutFile "C:\Users\MAI KHANH\jenkins-new.war"
  3. Verify the version inside the NEW war before swapping (avoid a wrong/corrupt file). 
    reading META-INF/MANIFEST.MFManifest-Version: 1.0
Implementation-Version: 2.568.2
Jenkins-Version: 2.568.2   # ✅ the version we want
  4. Stop the running Jenkins (kill the java PID, or Ctrl+C in its window). 
    PowerShell — stopStop-Process -Id 25764 -Force   # PID of java -jar jenkins.war
# Confirm port 9090 is closed before continuing
  5. Replace the war and restart. 
    PowerShell — replace & startMove-Item "C:\Users\MAI KHANH\jenkins-new.war" "C:\Users\MAI KHANH\jenkins.war" -Force
cd "C:\Users\MAI KHANH"
java -jar jenkins.war --httpPort=9090
  6. Verify the version via the X-Jenkins header (or the bottom-right of the page). 
    PowerShell — verify(Invoke-WebRequest http://localhost:9090/ -UseBasicParsing).Headers["X-Jenkins"]
# -> 2.568.2   ✅  and log: "Jenkins is fully up and running"
↩️ If it breaks → 30-second rollbackStop Jenkins → rename jenkins-2.568.1.war.bak back to jenkins.war → restart. Since JENKINS_HOME is untouched, all jobs/plugins/config stay intact.

Fixing the reverse-proxy warning

Independent of the upgrade. Just make the Jenkins URL match the real port:

Manage Jenkins → System → Jenkins LocationJenkins URL: http://localhost:8080/   # ❌ wrong port
Jenkins URL: http://localhost:9090/   # ✅ fix to match, then Save
✍️ Lessons learned (checklist)
  • ✅ Always back up JENKINS_HOME + the old war BEFORE upgrading — it's the only way back.
  • ✅ Download first, stop Jenkins second → downtime is only tens of seconds.
  • ✅ Back up JENKINS_HOME after stopping Jenkins → avoid copying locked files.
  • ✅ Read Jenkins-Version in the new war before swapping — confirm the right, uncorrupted build.
  • ✅ No need to back up the war/ folder (~108 MB) — Jenkins re-explodes it from the war on start.
  • ✅ After upgrading, go to Plugins → Updates, update plugins, then restart.
  • ✅ Verify via the X-Jenkins header or the "Jenkins is fully up and running" log — don't trust the UI alone.
⚠️ Common trapDon't click "Or Upgrade Automatically" when running via a bare java -jar — that path works well only for a service install (which can restart itself). For a manual war, upgrade manually as above so you keep control of rollback.
