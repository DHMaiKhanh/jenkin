Bài 3.1

Jenkinsfile là gì

🎯 Mục tiêuHiểu Jenkinsfile là gì, vì sao nên lưu pipeline dưới dạng code trong SCM, và khác biệt giữa job Pipeline với job Freestyle truyền thống.

Định nghĩa

Jenkinsfile là một text file chứa định nghĩa Jenkins Pipeline, viết bằng Groovy DSL (Declarative hoặc Scripted), và được checked-in vào source control cùng với code của dự án — thường đặt tên chính xác là Jenkinsfile ở thư mục gốc repo.

Jenkinsfilepipeline {
    agent any
    stages {
        stage('Build') {
            steps {
                echo 'Building...'
            }
        }
    }
}

Pipeline as Code — vì sao dùng SCM

Trước đây, cấu hình job Jenkins ("Freestyle") nằm hoàn toàn trong UI/database của Jenkins server — không có lịch sử thay đổi, khó review, khó tái tạo. Đưa pipeline vào Jenkinsfile nằm trong Git giải quyết các vấn đề đó.

Đặc điểmFreestyle jobPipeline (Jenkinsfile)
Nơi lưu cấu hìnhDatabase nội bộ JenkinsFile text trong repo Git
Kiểm soát phiên bảnKhông cóCó — commit, diff, blame, revert
Code reviewKhông thểĐược — qua Pull Request
Khả năng phục hồiMất cấu hình nếu Jenkins hỏngChỉ cần clone lại repo
Logic phức tạp (if/else, vòng lặp)Rất hạn chếĐầy đủ sức mạnh Groovy
🤔 Vì sao gọi là "pipeline as code"?Vì toàn bộ quy trình CI/CD (build → test → deploy) được mô tả bằng code thay vì click chuột trong UI. Điều này cho phép áp dụng mọi thực hành tốt của kỹ thuật phần mềm (review, versioning, testing) vào chính pipeline.

Jenkins tự phát hiện Jenkinsfile như thế nào

Khi tạo job kiểu Pipeline hoặc Multibranch Pipeline, bạn cấu hình "Pipeline script from SCM" trỏ đến repo Git và chỉ định đường dẫn file (mặc định Jenkinsfile ở root). Mỗi lần build, Jenkins checkout repo, đọc Jenkinsfile, và thực thi nó.

cấu trúc repomy-app/

├── package.json
└── README.md
💡 Multibranch PipelineVới Multibranch Pipeline, Jenkins tự động quét mọi branch trong repo, và branch nào có Jenkinsfile sẽ tự động được tạo thành một pipeline job riêng — không cần cấu hình tay từng branch.
⚠️ Đừng nhầm Jenkinsfile với script buildJenkinsfile điều phối các bước CI/CD cấp cao (checkout, build, test, deploy) — nó không thay thế công cụ build của dự án (Maven, npm, Gradle...). Bên trong step sh/bat, bạn vẫn gọi các công cụ đó bình thường.
✍️ Thực hànhTạo một repo Git mới, thêm file Jenkinsfile ở root với nội dung pipeline tối thiểu (agent any + 1 stage echo), commit và push. Sau đó tạo job Pipeline trỏ "from SCM" tới repo này.

Lesson 3.1

What is a Jenkinsfile

🎯 GoalUnderstand what a Jenkinsfile is, why pipelines should be stored as code in SCM, and how a Pipeline job differs from a traditional Freestyle job.

Definition

A Jenkinsfile is a text file that contains the definition of a Jenkins Pipeline, written in Groovy DSL (Declarative or Scripted), and is checked into source control alongside your project code — conventionally named exactly Jenkinsfile at the repository root.

Jenkinsfilepipeline {
    agent any
    stages {
        stage('Build') {
            steps {
                echo 'Building...'
            }
        }
    }
}

Pipeline as Code — why use SCM

Previously, Jenkins job configuration ("Freestyle") lived entirely in the Jenkins server's UI/database — no change history, hard to review, hard to reproduce. Putting the pipeline in a Jenkinsfile inside Git solves these problems.

AspectFreestyle jobPipeline (Jenkinsfile)
Where config livesJenkins internal databaseText file in Git repo
Version controlNoneYes — commit, diff, blame, revert
Code reviewNot possibleYes — via Pull Request
Disaster recoveryConfig lost if Jenkins breaksJust re-clone the repo
Complex logic (if/else, loops)Very limitedFull power of Groovy
🤔 Why "pipeline as code"?Because the entire CI/CD process (build → test → deploy) is described as code instead of clicked together in a UI. This lets you apply every good software-engineering practice (review, versioning, testing) to the pipeline itself.

How Jenkins discovers the Jenkinsfile

When creating a Pipeline or Multibranch Pipeline job, you configure "Pipeline script from SCM" pointing to the Git repo and specify the file path (defaults to Jenkinsfile at root). On every build, Jenkins checks out the repo, reads the Jenkinsfile, and executes it.

repo layoutmy-app/
├── Jenkinsfile          # Jenkins looks for this at root by default
├── src/
├── package.json
└── README.md
💡 Multibranch PipelineWith Multibranch Pipeline, Jenkins automatically scans every branch in the repo, and any branch containing a Jenkinsfile is automatically turned into its own pipeline job — no manual per-branch configuration needed.
⚠️ Don't confuse a Jenkinsfile with a build scriptThe Jenkinsfile orchestrates high-level CI/CD steps (checkout, build, test, deploy) — it does not replace your project's build tool (Maven, npm, Gradle...). Inside sh/bat steps you still call those tools normally.

Bài 3.2

Cú pháp Declarative Pipeline

🎯 Mục tiêuNắm được cấu trúc khung của một Declarative Pipeline: khối pipeline {} ở ngoài cùng, các section bắt buộc agent và stages, và khi nào nên chọn Declarative thay vì Scripted.

Khối pipeline{} — điểm khởi đầu bắt buộc

Mọi Declarative Pipeline phải bắt đầu bằng từ khóa pipeline, chứa bên trong là các "section" theo một cấu trúc cố định do Jenkins quy định — khác với Scripted Pipeline nơi bạn viết Groovy tự do.

Jenkinsfile — khung Declarativepipeline {
    agent any                 // ① BẮT BUỘC: chạy ở đâu

    environment {                 // ② tùy chọn: biến môi trường
        APP_ENV = 'staging'
    }

    options {                     // ③ tùy chọn: cấu hình pipeline
        timeout(time: 30, unit: 'MINUTES')
    }

    stages {                      // ④ BẮT BUỘC: ít nhất 1 stage
        stage('Build') {
            steps {
                sh './build.sh'
            }
        }
        stage('Test') {
            steps {
                sh './test.sh'
            }
        }
    }

    post {                        // ⑤ tùy chọn: hành động sau khi chạy
        always {
            echo 'Pipeline finished.'
        }
    }
}

Hai section duy nhất bắt buộc là agent (cấp cao nhất, quy định nơi thực thi) và stages (chứa ít nhất một stage). Mọi section khác đều tùy chọn.

Declarative vs Scripted

Tiêu chíDeclarativeScripted
Cú pháp gốcpipeline { ... }, cấu trúc cố địnhnode { ... }, Groovy thuần
Độ nghiêm ngặtBị giới hạn theo schema, dễ đọcTự do hoàn toàn, linh hoạt hơn
Đường cong học tậpThấp, dễ vàoCần biết Groovy sâu hơn
Validate cú phápCó (linter, Replay)Hạn chế
Được khuyến nghịCó — mặc định nên dùngKhi cần logic quá phức tạp
🤔 Vì sao Declarative là lựa chọn mặc định?Cú pháp có cấu trúc rõ ràng giúp Jenkins xác thực (validate) và hiển thị pipeline tốt hơn trong Blue Ocean/Stage View, dễ đọc với người mới, và vẫn có thể "thoát" ra Groovy thuần bằng khối script {} khi cần.

        stage('Demo') {

            }

}
⚠️ Lỗi cú pháp thường gặpQuên section stages, thiếu steps bên trong stage, hoặc đặt agent bên trong stages thay vì cấp cao nhất (trừ khi cố ý dùng agent riêng cho từng stage) đều khiến pipeline không parse được.

Lesson 3.2

Declarative Pipeline Syntax

🎯 GoalLearn the skeleton of a Declarative Pipeline: the outer pipeline {} block, the required agent and stages sections, and when to prefer Declarative over Scripted.

The pipeline{} block — the mandatory starting point

Every Declarative Pipeline must start with the pipeline keyword, containing "sections" in a fixed structure defined by Jenkins — unlike Scripted Pipeline where you write free-form Groovy.

Jenkinsfile — Declarative skeletonpipeline {
    agent any                 // ① REQUIRED: where to run

    environment {                 // ② optional: environment variables
        APP_ENV = 'staging'
    }

    options {                     // ③ optional: pipeline options
        timeout(time: 30, unit: 'MINUTES')
    }

    stages {                      // ④ REQUIRED: at least 1 stage
        stage('Build') {
            steps {
                sh './build.sh'
            }
        }
        stage('Test') {
            steps {
                sh './test.sh'
            }
        }
    }

    post {                        // ⑤ optional: post-run actions
        always {
            echo 'Pipeline finished.'
        }
    }
}

The only two required sections are agent (top level, defines where execution happens) and stages (containing at least one stage). Every other section is optional.

Declarative vs Scripted

CriteriaDeclarativeScripted
Root syntaxpipeline { ... }, fixed structurenode { ... }, pure Groovy
StrictnessConstrained by a schema, easy to readFully free-form, more flexible
Learning curveLow, easy to startRequires deeper Groovy knowledge
Syntax validationYes (linter, Replay)Limited
RecommendedYes — default choiceWhen logic is too complex for Declarative
🤔 Why is Declarative the default choice?The structured syntax lets Jenkins validate and render the pipeline better in Blue Ocean/Stage View, is easier for beginners to read, and can still "escape" into pure Groovy via a script {} block whenever needed.

Comments and formatting

Jenkinsfile// This is a single-line comment — plain Groovy syntax
pipeline {
    agent any
    stages {
        stage('Demo') {
            steps {
                echo 'Hello' /* trailing comment */
            }
        }
    }
}
⚠️ Common syntax mistakesForgetting the stages section, missing steps inside a stage, or placing agent inside stages instead of top level (unless intentionally using a per-stage agent) will all fail to parse.

Bài 3.3

agent, stages, steps chuyên sâu

🎯 Mục tiêuNắm rõ các loại agent, cách tổ chức nhiều stage, và các steps phổ biến nhất (sh, bat, echo, checkout scm, archiveArtifacts, junit).

Các loại agent

agent quy định Jenkins sẽ cấp phát executor/workspace nào để chạy pipeline (hoặc từng stage riêng).

các dạng agent// Chạy trên bất kỳ agent nào đang rảnh
agent any

// Không cấp agent mặc định — mỗi stage tự khai báo agent riêng
agent none

// Chỉ chạy trên node có label cụ thể
agent { label 'linux-docker' }

// Chạy bên trong một container Docker
agent {
    docker { image 'node:20-alpine' }
}
Dạng agentKhi nào dùng
agent anyPipeline đơn giản, không quan tâm node cụ thể
agent noneMuốn khai báo agent riêng cho từng stage
agent { label 'x' }Cần phần cứng/hệ điều hành/tool đặc thù (VD: Windows, GPU)
agent { docker 'image' }Cần môi trường build tái lập được, cô lập với host
🤔 Vì sao agent none + agent theo stage?Nhiều pipeline cần build trên Linux nhưng test trên Windows, hoặc chạy bước "Deploy" chỉ trên node có quyền production. Đặt agent none ở cấp pipeline rồi khai báo agent khác nhau cho mỗi stage giúp linh hoạt tối đa.

Nhiều stage & steps phổ biến

Jenkinsfilepipeline {
    agent any
    stages {
        stage('Checkout') {
            steps {
                checkout scm                     // lấy đúng commit đã trigger build
            }
        }
        stage('Build') {
            steps {
                sh 'npm install && npm run build'   // Linux/macOS
                bat 'npm install && npm run build'  // Windows
            }
        }
        stage('Test') {
            steps {
                sh 'npm test -- --reporter=junit'
            }
            post {
                always {
                    junit 'reports/junit.xml'      // publish kết quả test
                }
            }
        }
        stage('Archive') {
            steps {
                archiveArtifacts artifacts: 'dist/**', fingerprint: true
            }
        }
    }
}

Bảng nhanh các step phổ biến:

StepCông dụng
sh 'cmd'Chạy shell command trên Linux/macOS agent
bat 'cmd'Chạy command trên Windows agent
echo 'msg'In log thông báo
checkout scmCheckout đúng SCM/commit đã cấu hình cho job
archiveArtifactsLưu file build output để tải về sau

agent, stages, steps in Depth

🎯 GoalUnderstand the different kinds of agent, how to organize multiple stage blocks, and the most common steps (sh, bat, echo, checkout scm, archiveArtifacts, junit).

Kinds of agent

agent tells Jenkins which executor/workspace to allocate to run the pipeline (or an individual stage).

agent variants// Run on any available agent
agent any

// No default agent — each stage declares its own
agent none

// Only run on a node with a specific label
agent { label 'linux-docker' }

// Run inside a Docker container
agent {
    docker { image 'node:20-alpine' }
}
Agent formWhen to use
agent anySimple pipelines, node choice doesn't matter
agent noneWant to declare a different agent per stage
agent { label 'x' }Need specific hardware/OS/tools (e.g. Windows, GPU)
agent { docker 'image' }Need a reproducible build environment isolated from the host
🤔 Why agent none + per-stage agent?Many pipelines need to build on Linux but test on Windows, or run a "Deploy" step only on a node with production access. Setting agent none at the pipeline level and declaring different agents per stage gives maximum flexibility.

Multiple stages & common steps

Jenkinsfilepipeline {
    agent any
    stages {
        stage('Checkout') {
            steps {
                checkout scm                     // fetch the exact commit that triggered the build
            }
        }
        stage('Build') {
            steps {
                sh 'npm install && npm run build'   // Linux/macOS
                bat 'npm install && npm run build'  // Windows
            }
        }
        stage('Test') {
            steps {
                sh 'npm test -- --reporter=junit'
            }
            post {
                always {
                    junit 'reports/junit.xml'      // publish test results
                }
            }
        }
        stage('Archive') {
            steps {
                archiveArtifacts artifacts: 'dist/**', fingerprint: true
            }
        }
    }
}

junitPublish JUnit XML test results to the Jenkins UI

⚠️ sh vs batUsing sh on a Windows agent (or bat on a Linux agent) fails immediately with "not found" — always match the step to the agent's actual OS.

The post Section & environment

🎯 GoalLearn to use the post section with the always/success/failure/unstable/changed/cleanup conditions to send notifications or clean up, and understand the basics of the environment block.

The post conditions

ConditionRuns when
alwaysAlways, regardless of the pipeline result
successThe whole pipeline succeeded
failureThe pipeline failed
unstableResult is "unstable" (e.g. some tests failed but build still passed)
changedResult differs from the previous run (e.g. went from fail to pass)
cleanupRuns last, after every other condition — typically used to clean the workspace

A realistic post example: notifications by outcome

                sh './gradlew build test'
            }

                    junit 'build/test-results/**/*.xml'
                }
            }
        }

    post {
        success {
            echo "✅ Build ${env.APP_VERSION} succeeded — notifying ${env.SLACK_CHANNEL}"
            // slackSend(channel: env.SLACK_CHANNEL, color: 'good', message: "Build OK: ${env.APP_VERSION}")

Cấu trúc Scripted Pipeline

Scripted Pipeline là Groovy thuần, thực thi tuần tự theo mã lệnh — không bị ràng buộc bởi schema cố định như Declarative. Khối cấp cao nhất là node {} thay vì pipeline {}.

Không cần viết toàn bộ pipeline theo Scripted — Declarative cho phép "thoát" ra Groovy thuần trong một step bằng khối script {}.

Control flow Groovy: for, if, try/catch

Jenkinsfile — Scriptednode {
    def environments = ['dev', 'staging', 'prod']

    stage('Deploy tuần tự') {
        for (env in environments) {
            if (env == 'prod') {
                echo "⚠️ Bỏ qua prod — cần duyệt tay"
                continue
            }
            echo "Deploying to ${env}..."
        }
    }

    stage('Chạy test có xử lý lỗi') {
        try {
            sh './run-integration-tests.sh'
        } catch (Exception e) {
            echo "Test thất bại: ${e.getMessage()}"
            currentBuild.result = 'UNSTABLE'
        } finally {
            archiveArtifacts artifacts: 'test-results/**', allowEmptyArchive: true
        }
    }
}

⚠️ Scripted khó review và dễ lỗi runtime hơnVì không có schema cố định, lỗi cú pháp/logic trong Scripted Pipeline thường chỉ phát hiện lúc chạy thật (runtime), không được validate trước như Declarative. Luôn viết test/thử nhỏ trước khi áp dụng logic phức tạp.

Scripted Pipeline structure

Scripted Pipeline is pure Groovy, executed sequentially — not constrained by a fixed schema like Declarative. The top-level block is node {} instead of pipeline {}.

Jenkinsfile — Scriptednode {                                  // ① allocates an executor
    stage('Checkout') {              // ② stage() is a Groovy function, not a fixed block
        checkout scm
    }
    stage('Build') {
        sh 'npm install'
        sh 'npm run build'
    }
    stage('Test') {
        sh 'npm test'
    }
}
AspectScripted
Root blocknode { ... }
stageGroovy function stage('Name') { ... }, no mandatory steps wrapper
Control flowif/else, for, while, try/catch used directly, no need to wrap in script{}
When to useComplex logic: dynamic loops over a list, sophisticated error handling, generating stages dynamically at runtime
🤔 When to pick Scripted over Declarative?When you need to generate stages dynamically (e.g. loop over a list of modules and build each one), handle errors with nested try/catch, or call advanced Groovy APIs. For 90% of typical pipelines, Declarative plus a script{} block when needed is enough.

The script{} block inside Declarative

You don't need to write the whole pipeline as Scripted — Declarative lets you "escape" into pure Groovy inside a step via a script {} block.

Jenkinsfile — Declarative + script{}pipeline {
    agent any
    stages {
        stage('Build modules') {
            steps {
                script {
                    def modules = ['api', 'web', 'worker']
                    for (m in modules) {
                        echo "Building module: ${m}"
                        sh "./gradlew :${m}:build"
                    }
                }
            }
        }
    }
}

Groovy control flow: for, if, try/catch

Jenkinsfile — Scriptednode {
    def environments = ['dev', 'staging', 'prod']

    stage('Sequential deploy') {
        for (env in environments) {
            if (env == 'prod') {
                echo "⚠️ Skipping prod — needs manual approval"
                continue
            }
            echo "Deploying to ${env}..."
        }
    }

    stage('Run tests with error handling') {
        try {
            sh './run-integration-tests.sh'
        } catch (Exception e) {
            echo "Tests failed: ${e.getMessage()}"
            currentBuild.result = 'UNSTABLE'
        } finally {
            archiveArtifacts artifacts: 'test-results/**', allowEmptyArchive: true
        }
    }
}
💡 sh can return a status codeUse sh(script: '...', returnStatus: true) to get the exit code instead of letting the step fail the pipeline automatically — handy when you want to decide error handling yourself inside try/catch.
⚠️ Scripted is harder to review and more runtime-fragileBecause there's no fixed schema, syntax/logic errors in Scripted Pipeline are often only caught at runtime, unlike Declarative which can be validated up front. Always test small pieces of logic before applying complex changes.

📚 5 real-world examples · Scripted Pipeline
  1. Minimal Scripted Pipeline with node and 1 stage. 
    Jenkinsfilenode {
    stage('Hello') {
        echo 'Hello from Scripted'
    }
}
  2. Specify a label for the node. 
    Jenkinsfilenode('linux') {
    stage('Build') { sh 'make' }
}
  3. for loop building multiple modules. 
    Jenkinsfilenode {
    def mods = ['core', 'api']
    stage('Build all') {
        for (m in mods) { sh "./build.sh ${m}" }
    }
}
  4. if/else deciding deployment by branch. 
    Jenkinsfilenode {
    stage('Deploy') {
        if (env.BRANCH_NAME == 'main') {
            sh './deploy.sh prod'
        } else {
            echo 'Not main — skipping deploy'
        }
    }
}
  5. try/catch/finally around a sh step that might fail. 
    Jenkinsfilenode {
    stage('Test') {
        try {
            sh 'npm test'
        } catch (e) {
            currentBuild.result = 'UNSTABLE'
        } finally {
            junit 'reports/*.xml'
        }
    }
}
