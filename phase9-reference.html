Reference & Best PracticesReference & Best Practices

Mục tiêu giai đoạn: thành thạo các công cụ tra cứu/điều khiển Jenkins từ xa (CLI, REST API), biết cách tự tra cứu cú pháp Pipeline, chẩn đoán sự cố thường gặp, và áp dụng các thực hành tốt nhất được Jenkins khuyến nghị chính thức.Stage goal: master Jenkins' remote tooling (CLI, REST API), know how to self-serve Pipeline syntax lookups, diagnose common issues, and apply the official Jenkins-recommended best practices.

Bài 9.1

Jenkins CLI

🎯 Mục tiêuTải và dùng được jenkins-cli.jar để điều khiển Jenkins từ terminal: liệt kê job, build, xem console log, tạo/cập nhật job bằng XML, và chạy script Groovy từ xa.

Tải & xác thực

CLI client là một file .jar được chính server Jenkins của bạn cung cấp — luôn tải đúng bản khớp version server để tránh lỗi không tương thích.

terminal# Tải jenkins-cli.jar từ chính server đang chạy
curl -O http://localhost:8080/jnlpJars/jenkins-cli.jar

# Xác thực bằng API token (khuyến nghị) — lấy token tại
# /user/<username>/security -> "Add new Token"
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:11aa22bb33cc44dd who-am-i
Cách xác thựcCú phápGhi chú
API token-auth user:tokenCách được khuyến nghị, không lộ mật khẩu thật.
File auth-auth @/path/to/fileNội dung file là user:token, tránh lộ trong history shell.
SSH key-i ~/.ssh/id_rsaCần bật cổng SSH CLI trong "Configure Global Security" và gắn public key vào user.
🤔 Vì sao ưu tiên API token thay vì mật khẩu?Token có thể thu hồi độc lập, không lộ mật khẩu đăng nhập chính, và có thể giới hạn phạm vi. Đây cũng là cách REST API và nhiều tích hợp CI khác dùng để xác thực.

Các lệnh thường dùng

terminal# Liệt kê toàn bộ job
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN list-jobs

# Trigger build và chờ tới khi xong (-f = follow/wait, thoát code = kết quả build)
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN build my-job -f

# Trigger build kèm tham số
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN build my-job -f -p BRANCH=main

# Xem console output (log) của job đang chạy, theo real-time
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN console my-job -f

# Tạo job mới từ file config.xml
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN create-job new-job < config.xml

# Cập nhật job đã có từ file XML
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN update-job my-job < config.xml

# Xuất config.xml của job hiện có (hữu ích để nhân bản/backup)
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN get-job my-job > config.xml

# Chạy script Groovy trực tiếp trên server (rất mạnh — cẩn trọng quyền hạn)
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN groovy = < script.groovy
💡 Xem toàn bộ lệnh khả dụngChạy java -jar jenkins-cli.jar -s URL -auth user:token help để liệt kê mọi lệnh — danh sách phụ thuộc plugin đang cài, có thể khác nhau giữa các Jenkins.
⚠️ Rủi ro của lệnh groovyGroovy script chạy trực tiếp trong JVM của Jenkins controller với quyền đầy đủ — có thể đọc/ghi bất cứ thứ gì, kể cả credentials đã lưu. Chỉ cấp quyền chạy CLI groovy cho người dùng thật sự tin cậy (thường tương đương quyền Admin).
✍️ Thực hànhTải jenkins-cli.jar từ Jenkins của bạn, tạo API token, rồi dùng list-jobs để liệt kê job, sau đó build <job> -f để trigger một build và xem kết quả ngay trên terminal.

Lesson 9.1

Jenkins CLI

🎯 GoalDownload and use jenkins-cli.jar to control Jenkins from a terminal: listing jobs, building, viewing console logs, creating/updating jobs via XML, and running remote Groovy scripts.

Download & authenticate

The CLI client is a .jar served by your own Jenkins instance — always download the copy matching your server version to avoid incompatibility.

terminal# Download jenkins-cli.jar from the running server
curl -O http://localhost:8080/jnlpJars/jenkins-cli.jar

# Authenticate with an API token (recommended) — generate one at
# /user/<username>/security -> "Add new Token"
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:11aa22bb33cc44dd who-am-i
Auth methodSyntaxNotes
API token-auth user:tokenRecommended, doesn't expose the real password.
Auth file-auth @/path/to/fileFile content is user:token, avoids leaking it in shell history.
SSH key-i ~/.ssh/id_rsaRequires enabling the SSH CLI port in "Configure Global Security" and attaching a public key to the user.
🤔 Why prefer API tokens over passwords?Tokens can be revoked independently, don't expose the login password, and can be scoped. It's also how the REST API and many CI integrations authenticate.

Common commands

terminal# List every job
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN list-jobs

# Trigger a build and wait for it to finish (-f = follow/wait, exit code = build result)
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN build my-job -f

# Trigger a parameterized build
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN build my-job -f -p BRANCH=main

# Stream the console output (log) of a running job
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN console my-job -f

# Create a new job from a config.xml file
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN create-job new-job < config.xml

# Update an existing job from an XML file
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN update-job my-job < config.xml

# Export a job's config.xml (useful for cloning/backup)
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN get-job my-job > config.xml

# Run a Groovy script directly on the server (very powerful — be careful with permissions)
java -jar jenkins-cli.jar -s http://localhost:8080/ -auth admin:TOKEN groovy = < script.groovy
💡 See every available commandRun java -jar jenkins-cli.jar -s URL -auth user:token help to list all commands — the list depends on installed plugins and can vary between instances.
⚠️ Risk of the groovy commandA Groovy script runs directly inside the Jenkins controller's JVM with full privileges — it can read/write anything, including stored credentials. Only grant CLI groovy execution to fully trusted users (effectively equivalent to Admin).
✍️ ExerciseDownload jenkins-cli.jar from your Jenkins, create an API token, then use list-jobs to list jobs, and build <job> -f to trigger a build and see the result right in your terminal.

Bài 9.2

REST API

🎯 Mục tiêuĐọc dữ liệu Jenkins (job, build, queue...) qua endpoint JSON/XML/Python, trigger build từ xa bằng POST có token và CSRF crumb, và đọc trạng thái/console log bằng curl.

Endpoint dữ liệu — chỉ cần thêm hậu tố

Hầu hết trang trong Jenkins đều có phiên bản dữ liệu thô — chỉ cần thêm /api/json, /api/xml hoặc /api/python vào cuối URL.

terminal# Thông tin job dạng JSON (danh sách build, health, param...)
curl -u admin:TOKEN http://localhost:8080/job/my-job/api/json?pretty=true

# Thông tin một build cụ thể
curl -u admin:TOKEN http://localhost:8080/job/my-job/42/api/json?pretty=true

# Chỉ lấy đúng field cần, dùng tree= để giảm payload
curl -u admin:TOKEN "http://localhost:8080/job/my-job/api/json?tree=builds[number,result,timestamp]"

# Dạng XML hoặc Python literal
curl -u admin:TOKEN http://localhost:8080/job/my-job/api/xml
curl -u admin:TOKEN http://localhost:8080/job/my-job/api/python
🤔 Vì sao dùng tree=?Response mặc định có thể rất lớn (toàn bộ lịch sử build, artifact...). Tham số tree lọc field ngay tại server, giảm băng thông và giúp script parse nhanh hơn.

Trigger build từ xa — cần crumb (CSRF)

Theo mặc định, Jenkins bật CSRF protection, nên các request POST (kể cả trigger build) cần một "crumb" hợp lệ kèm theo, trừ khi bạn dùng API token qua Basic Auth kết hợp cấu hình cho phép bỏ crumb cho request có auth.

terminal# 1) Lấy crumb
CRUMB=$(curl -u admin:TOKEN "http://localhost:8080/crumbIssuer/api/json" \
  | jq -r '.crumbRequestField + "=" + .crumb')

# 2) Trigger build kèm crumb
curl -u admin:TOKEN -X POST -H "$CRUMB" \
  http://localhost:8080/job/my-job/build

# Trigger build có tham số (dùng buildWithParameters)
curl -u admin:TOKEN -X POST -H "$CRUMB" \
  "http://localhost:8080/job/my-job/buildWithParameters?ENV=staging&VERSION=1.2.3"

# Trigger qua "remote build token" thay vì user/password (bật trong cấu hình job)
curl -X POST "http://localhost:8080/job/my-job/build?token=MY_REMOTE_TOKEN"
EndpointMethodDùng để
/job/<name>/api/jsonGETThông tin job, danh sách build
/job/<name>/buildPOSTTrigger build không tham số
/job/<name>/buildWithParametersPOSTTrigger build có tham số
/job/<name>/<n>/api/jsonGETChi tiết build số n
/job/<name>/<n>/consoleTextGETConsole log dạng text thuần
/queue/api/jsonGETXem hàng đợi build
/crumbIssuer/api/jsonGETLấy crumb để dùng cho POST
💡 Đọc console log qua APIGET /job/<name>/<n>/consoleText trả về log dạng text thuần — rất tiện để script CI ngoài polling trạng thái build.
⚠️ Đừng tắt CSRF protection để "cho tiện"Một số hướng dẫn cũ khuyên tắt hẳn CSRF crumb để đơn giản hóa script — đây là rủi ro bảo mật nghiêm trọng (mở đường cho cross-site request forgery). Luôn lấy crumb đúng cách hoặc dùng remote build token có giới hạn phạm vi.
✍️ Thực hànhViết một script bash: lấy crumb, trigger build có tham số cho một job thật, sau đó poll /lastBuild/api/json mỗi 5 giây cho tới khi result khác null, in ra kết quả cuối cùng.
📚 5 ví dụ thực tế · REST API
  1. Lấy trạng thái build gần nhất của một job. 
    terminalcurl -u admin:TOKEN http://localhost:8080/job/my-job/lastBuild/api/json?tree=result,number
  2. Trigger build kèm crumb bằng curl.

curl -u admin:TOKEN -X POST -H "$CRUMB" http://localhost:8080/job/my-job/build
  3. Tải console log của build số 87 ra file. 
    terminalcurl -u admin:TOKEN http://localhost:8080/job/my-job/87/consoleText -o build-87.log
  4. Kiểm tra số build đang chờ trong hàng đợi. 
    terminalcurl -u admin:TOKEN http://localhost:8080/queue/api/json?tree=items[task[name]]

Lesson 9.2

REST API

🎯 GoalRead Jenkins data (jobs, builds, queue...) via JSON/XML/Python endpoints, trigger builds remotely with a POST carrying a token and CSRF crumb, and read status/console logs with curl.

Data endpoints — just append a suffix

Most Jenkins pages have a raw-data version — just append /api/json, /api/xml or /api/python to the URL.

terminal# Job info as JSON (build list, health, params...)
curl -u admin:TOKEN http://localhost:8080/job/my-job/api/json?pretty=true

# Info for one specific build
curl -u admin:TOKEN http://localhost:8080/job/my-job/42/api/json?pretty=true

# Fetch only the fields you need with tree= to shrink the payload
curl -u admin:TOKEN "http://localhost:8080/job/my-job/api/json?tree=builds[number,result,timestamp]"

# XML or Python literal form
curl -u admin:TOKEN http://localhost:8080/job/my-job/api/xml
curl -u admin:TOKEN http://localhost:8080/job/my-job/api/python
🤔 Why use tree=?The default response can be huge (full build history, artifacts...). The tree parameter filters fields server-side, cutting bandwidth and making scripts parse faster.

Triggering builds remotely — crumb (CSRF) required

By default Jenkins enables CSRF protection, so POST requests (including triggering builds) need a valid "crumb" attached, unless you use an API token via Basic Auth combined with a config that exempts authenticated requests from the crumb check.

terminal# 1) Fetch a crumb
CRUMB=$(curl -u admin:TOKEN "http://localhost:8080/crumbIssuer/api/json" \
  | jq -r '.crumbRequestField + "=" + .crumb')

# 2) Trigger a build with the crumb
curl -u admin:TOKEN -X POST -H "$CRUMB" \
  http://localhost:8080/job/my-job/build

# Trigger a parameterized build (use buildWithParameters)
curl -u admin:TOKEN -X POST -H "$CRUMB" \
  "http://localhost:8080/job/my-job/buildWithParameters?ENV=staging&VERSION=1.2.3"

# Trigger via a "remote build token" instead of user/password (enabled in job config)
curl -X POST "http://localhost:8080/job/my-job/build?token=MY_REMOTE_TOKEN"
EndpointMethodPurpose
/job/<name>/api/jsonGETJob info, build list
/job/<name>/buildPOSTTrigger a build without params
/job/<name>/buildWithParametersPOSTTrigger a build with params
/job/<name>/<n>/api/jsonGETDetails of build number n
/job/<name>/<n>/consoleTextGETPlain-text console log
/queue/api/jsonGETView the build queue
/crumbIssuer/api/jsonGETFetch a crumb for POST requests
💡 Reading console logs via the APIGET /job/<name>/<n>/consoleText returns a plain-text log — very handy for an external CI script polling build status.
⚠️ Don't disable CSRF protection for "convenience"Some older guides suggest disabling the CSRF crumb entirely to simplify scripts — this is a serious security risk (opens the door to cross-site request forgery). Always fetch the crumb properly or use a scoped remote build token.
✍️ ExerciseWrite a bash script: fetch a crumb, trigger a parameterized build for a real job, then poll /lastBuild/api/json every 5 seconds until result is no longer null, and print the final result.

Bài 9.3

Tra cứu cú pháp Pipeline

🎯 Mục tiêuBiết dùng công cụ "Pipeline Syntax" (Snippet Generator) trong UI để tự sinh cú pháp step chính xác, nắm các biến toàn cục env/currentBuild/params, và có sẵn bảng cheat-sheet các step hay dùng nhất.

Snippet Generator — đừng nhớ, hãy sinh

Mọi job Pipeline đều có link "Pipeline Syntax" ở sidebar. Trong đó, mục Snippet Generator cho bạn chọn step từ dropdown, điền form (giống một UI job cũ), rồi bấm "Generate Pipeline Script" để lấy đúng cú pháp Groovy — cực hữu ích cho các step phức tạp như withCredentials hay step của plugin bên thứ ba.

Common Troubleshooting

🎯 GoalRead stack traces in console output, tell FAILURE apart from UNSTABLE, recognize disk-space issues, agent-offline causes, plugin conflicts after upgrades, and know how to use /log plus support bundles to diagnose problems.

Reading console output & stack traces

Always read bottom-up — the root cause line is usually near the end; lines above are often just consequences. In Pipeline, look for lines starting with ERROR: or Also: (when errors are nested), and which stage was running when the failure occurred (highlighted in "Stage View" or [Pipeline] { (Stage Name)).

console output[Pipeline] sh
+ npm test
...
Error: Cannot find module 'jest'
    at Function.Module._resolveFilename (node:internal/modules/cjs/loader:1075:15)
    ...
[Pipeline] }
[Pipeline] // stage
ERROR: script returned exit code 1
Finished: FAILURE
StatusMeaningTypical cause
SUCCESSEvery step/stage passed—
UNSTABLEBuild finished but reported a bad signal (usually failed tests but the publish step still ran)junit publisher saw failed tests, or a step called currentBuild.result = 'UNSTABLE'
FAILUREA step threw an error, stopping the Pipeline outrightNon-zero sh exit code, a Groovy exception, a timeout
ABORTEDManually cancelled or killed by timeoutUser clicked Abort, or a timeout(){} expired
🤔 Why can a build be UNSTABLE instead of FAILURE?Many publishers (like junit) are designed to not stop the whole pipeline just because a few tests failed — they mark the build UNSTABLE so you still get artifacts/reports, instead of losing everything to a hard FAILURE.

Disk space exhaustion & bloated workspaces

The most common reason a controller/agent grinds to a halt: unpruned build history and workspaces, with artifacts piling up across thousands of builds.

Jenkinsfile — cap historyoptions {
  buildDiscarder(logRotator(numToKeepStr: '30', artifactNumToKeepStr: '10'))
}
  • Use the Disk Usage plugin or Workspace Cleanup (cleanWs()) to clear workspaces after each build.
  • Check JENKINS_HOME (especially jobs/*/builds) when the controller shows a "Disk space" warning on the dashboard.

Best Practices

🎯 Mục tiêuGhi nhớ các thực hành tốt nhất được Jenkins khuyến nghị chính thức: Jenkinsfile trong SCM, Declarative vs Scripted, Shared Library, không build nặng trên controller, pin version, fail fast, pipeline idempotent.

Luôn để Jenkinsfile trong SCM

Đừng viết pipeline trực tiếp trong ô "Pipeline script" của UI job — hãy commit Jenkinsfile cùng repo với code, dùng "Pipeline script from SCM". Nhờ vậy pipeline được review, versioned, và rollback được cùng nhịp với code.

Job configPipeline: Definition = "Pipeline script from SCM"
  SCM: Git
  Script Path: Jenkinsfile

Declarative vs Scripted

DeclarativeScripted
Cú phápCấu trúc chặt pipeline {}Groovy tự do trong node {}
Dễ đọc / validateCao — linter kiểm được cấu trúcThấp hơn — linh hoạt hơn nhưng dễ sai
Khi nào chọnMặc định cho hầu hết pipelineKhi cần logic điều khiển phức tạp mà Declarative không hỗ trợ (vẫn dùng được qua block script {})
🤔 Vì sao Jenkins khuyến nghị Declarative trước?Declarative có cấu trúc cố định giúp công cụ (linter, Blue Ocean, Snippet Generator) hiểu và validate pipeline tốt hơn, giảm lỗi cú pháp và dễ onboard người mới hơn Scripted thuần.

Shared Libraries — đừng lặp lại chính mình

Jenkinsfile@Library('my-shared-lib@main') _

pipeline {
  agent any
  stages {
    stage('Build & Deploy') {
      steps {
        standardBuildAndDeploy(service: 'checkout-api', env: 'staging')
      }
    }
  }
}

Khi nhiều Jenkinsfile lặp lại cùng logic (build Docker, deploy, thông báo Slack...), hãy trích xuất thành Shared Library (vars/*.groovy) dùng chung, versioned và test được độc lập.

Các nguyên tắc khác

  • Không build nặng trên controller: controller chỉ nên điều phối; luôn set agent chạy trên agent/label riêng, tránh agent none + step nặng chạy nhầm trên controller.
  • Pin version: pin cả version plugin và version tool (tools { jdk 'jdk17' }, Docker image tag cụ thể thay vì latest) để build không bất ngờ đổi hành vi.
  • Fail fast: đặt bước kiểm tra rẻ/nhanh (lint, unit test) trước bước tốn kém (deploy, integration test) để phát hiện lỗi sớm.
  • Idempotent & stateless mỗi build: mỗi lần chạy nên dùng workspace sạch, không phụ thuộc trạng thái để lại từ build trước; dùng cleanWs() hoặc container tạm.
Jenkinsfilepipeline {
  agent { label 'linux-docker' }   // không chạy trên controller
  tools { jdk 'jdk17' }               // pin version tool
  options { buildDiscarder(logRotator(numToKeepStr: '30')) }
  stages {
    stage('Lint')  { steps { sh 'npm run lint' } }      // rẻ, chạy trước
    stage('Unit')  { steps { sh 'npm test' } }
    stage('Deploy') { steps { sh './deploy.sh' } }   // tốn kém, chạy sau
  }
  post { always { cleanWs() } }               // mỗi build sạch sẽ
}

Lesson 9.5

Best Practices

🎯 GoalInternalize the officially recommended Jenkins best practices: Jenkinsfile in SCM, Declarative vs Scripted, Shared Libraries, avoiding heavy builds on the controller, pinning versions, failing fast, and idempotent pipelines.

Always keep the Jenkinsfile in SCM

Don't write pipelines directly into the job UI's "Pipeline script" box — commit a Jenkinsfile alongside the code and use "Pipeline script from SCM". This way the pipeline gets reviewed, versioned, and can be rolled back in lockstep with the code.

Job configPipeline: Definition = "Pipeline script from SCM"
  SCM: Git
  Script Path: Jenkinsfile

Declarative vs Scripted

DeclarativeScripted
SyntaxRigid pipeline {} structureFree-form Groovy inside node {}
Readability / validationHigh — linters can check structureLower — more flexible but easier to get wrong
When to pickDefault for most pipelinesWhen you need complex control-flow logic Declarative doesn't support (still reachable via a script {} block)
🤔 Why does Jenkins recommend Declarative first?Declarative's fixed structure lets tooling (linters, Blue Ocean, the Snippet Generator) understand and validate pipelines better, reducing syntax errors and easing onboarding compared to plain Scripted.

Shared Libraries — don't repeat yourself

Jenkinsfile@Library('my-shared-lib@main') _

pipeline {
  agent any
  stages {
    stage('Build & Deploy') {
      steps {
        standardBuildAndDeploy(service: 'checkout-api', env: 'staging')
      }
    }
  }
}

When multiple Jenkinsfiles repeat the same logic (Docker builds, deploys, Slack notifications...), extract it into a Shared Library (vars/*.groovy) that's shared, versioned, and independently testable.

Other principles

  • Don't run heavy builds on the controller: the controller should only orchestrate; always set agent to run on a dedicated agent/label, avoiding agent none plus heavy steps accidentally running on the controller.
  • Pin versions: pin both plugin versions and tool versions (tools { jdk 'jdk17' }, specific Docker image tags instead of latest) so builds don't silently change behavior.
  • Fail fast: put cheap/fast checks (lint, unit tests) before expensive ones (deploy, integration tests) to catch failures early.
  • Idempotent & stateless per build: every run should start from a clean workspace, not depend on state left by a previous build; use cleanWs() or ephemeral containers.
Jenkinsfilepipeline {
  agent { label 'linux-docker' }   // not on the controller
  tools { jdk 'jdk17' }               // pin the tool version
  options { buildDiscarder(logRotator(numToKeepStr: '30')) }
  stages {
    stage('Lint')  { steps { sh 'npm run lint' } }      // cheap, runs first
    stage('Unit')  { steps { sh 'npm test' } }
    stage('Deploy') { steps { sh './deploy.sh' } }   // expensive, runs later
  }
  post { always { cleanWs() } }               // clean slate every build
}
⚠️ "Latest" is the enemy of stable buildsUsing image: 'node:latest' or leaving plugins unpinned means today's build can differ from yesterday's even with unchanged code — very hard to debug. Always pin specific tags/versions.
