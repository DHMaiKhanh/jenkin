Scaling & Distributed Builds

Mục tiêu giai đoạn: hiểu vì sao và làm thế nào để mở rộng Jenkins ra nhiều máy build, từ agent SSH/JNLP thủ công đến agent Docker và Kubernetes co giãn tự động, và agent cloud theo nhu cầu.Stage goal: understand why and how to scale Jenkins across many build machines — from manual SSH/JNLP agents to elastic Docker and Kubernetes agents, and on-demand cloud agents.

Bài 7.1

Kiến trúc Controller/Agent

🎯 Mục tiêuHiểu vì sao Jenkins tách "controller" (điều phối) khỏi "agent" (thực thi build), khái niệm executor, label, node tích hợp sẵn (built-in node), và cách nghĩ về scale ngang vs scale dọc.

Vì sao phải tách controller khỏi agent?

Controller (trước đây gọi là "master") chịu trách nhiệm: lưu cấu hình, lập lịch job, phục vụ UI, điều phối plugin. Nếu build cũng chạy ngay trên controller, tài nguyên CPU/RAM/ổ đĩa bị build "ăn" mất, ảnh hưởng đến sự ổn định và bảo mật của toàn hệ thống Jenkins. Vì vậy thực hành khuyến nghị chính thức là: không build trên controller (built-in node) trong môi trường production — chuyển toàn bộ việc build sang các agent riêng biệt.

Executor & Label

Mỗi node (controller hoặc agent) có một số lượng executor — mỗi executor là một "khe" (slot) có thể chạy một build tại một thời điểm. Label là nhãn gắn cho node để Pipeline chọn đúng nơi chạy.

Jenkinsfilepipeline {
  agent { label 'linux && docker' }  // chỉ chạy trên agent có cả 2 label
  stages {
    stage('Build') {
      steps { sh 'make build' }
    }
  }
}
Khái niệmÝ nghĩaVí dụ
NodeMột máy (vật lý/ảo/container) có thể chạy buildController, agent-linux-01
ExecutorSố build đồng thời tối đa trên 1 node4 executor → chạy tối đa 4 build song song
LabelNhãn để định tuyến job đến đúng nodelinux, docker, gpu
Built-in nodeNode chạy ngay trên controllerKhông nên dùng để build production

Scale ngang vs scale dọc

  • Scale dọc (vertical): tăng CPU/RAM cho một agent — đơn giản nhưng có giới hạn phần cứng và điểm nghẽn duy nhất.
  • Scale ngang (horizontal): thêm nhiều agent — chịu tải tốt hơn, chống lỗi tốt hơn (một agent chết không ảnh hưởng agent khác), là hướng đi khuyến nghị khi số lượng job/team tăng.
🤔 Vì sao nên offload build khỏi controller?Controller là "bộ não" duy nhất của toàn hệ thống Jenkins — nếu nó sập, mọi job đều dừng. Giữ controller nhẹ (chỉ điều phối) và đẩy toàn bộ workload build ra agent giúp controller luôn phản hồi nhanh, giảm rủi ro bảo mật (build code lạ chạy trên máy cô lập) và cho phép scale từng phần độc lập.
⚠️ Built-in node = 0 executor trong productionMột sai lầm phổ biến là để mặc định built-in node có executor > 0 rồi build luôn trên đó. Hãy đặt số executor của built-in node về 0 và chỉ dùng label để định tuyến build sang các agent chuyên dụng.
✍️ Thực hànhVào Manage Jenkins › Nodes, đặt số executor của built-in node về 0, sau đó viết một Jenkinsfile có agent { label 'linux' } và kiểm tra build bị "pending" nếu chưa có agent nào gắn label đó.

Lesson 7.1

Controller/Agent Architecture

🎯 GoalUnderstand why Jenkins separates the "controller" (orchestration) from "agents" (build execution), the concepts of executors and labels, the built-in node, and how to think about horizontal vs vertical scaling.

Why separate controller from agents?

The controller (formerly "master") is responsible for storing configuration, scheduling jobs, serving the UI, and coordinating plugins. If builds also run directly on the controller, they consume CPU/RAM/disk that the controller needs, hurting stability and security. That's why official best practice is: don't build on the controller (built-in node) in production — move all build work to dedicated agents.

Executors & Labels

Each node (controller or agent) has a number of executors — each executor is a "slot" that can run one build at a time. A label is a tag attached to a node so Pipelines can pick the right place to run.

Jenkinsfilepipeline {
  agent { label 'linux && docker' }  // only runs on an agent with both labels
  stages {
    stage('Build') {
      steps { sh 'make build' }
    }
  }
}
ConceptMeaningExample
NodeA machine (physical/virtual/container) that can run buildsController, agent-linux-01
ExecutorMax concurrent builds on 1 node4 executors → up to 4 parallel builds
LabelTag used to route a job to the right nodelinux, docker, gpu
Built-in nodeNode running directly on the controllerNot recommended for production builds

Horizontal vs vertical scaling

  • Vertical scaling: give one agent more CPU/RAM — simple but limited by hardware and a single bottleneck.
  • Horizontal scaling: add more agents — handles more load, more fault-tolerant (one agent dying doesn't affect others), the recommended direction as job/team count grows.
🤔 Why offload builds from the controller?The controller is the single "brain" of the whole Jenkins system — if it goes down, every job stops. Keeping the controller lean (orchestration only) and pushing all build workload to agents keeps the controller responsive, reduces security risk (untrusted build code runs on an isolated machine), and lets you scale each part independently.
⚠️ Built-in node = 0 executors in productionA common mistake is leaving the built-in node's executor count above 0 and building there. Set the built-in node's executor count to 0 and use labels to route builds to dedicated agents only.
✍️ ExerciseGo to Manage Jenkins › Nodes, set the built-in node's executor count to 0, then write a Jenkinsfile with agent { label 'linux' } and observe the build stay "pending" until an agent with that label exists.

Bài 7.2

Agent SSH & JNLP/WebSocket

🎯 Mục tiêuBiết cách thêm một agent SSH thường trực từng bước, hiểu cơ chế agent JNLP/inbound kết nối qua agent.jar, các vấn đề firewall/port, và cách giới hạn job theo label.

Thêm agent qua SSH — từng bước

  1. Chuẩn bị máy Linux/Windows đã cài Java (JDK tương thích với controller), tạo user chuyên dụng (vd jenkins) với quyền vào thư mục làm việc.
  2. Trên controller: Manage Jenkins › Nodes › New Node, đặt tên, chọn "Permanent Agent".
  3. Điền Remote root directory (vd /home/jenkins/agent), gắn Labels (vd linux docker).
  4. Chọn Launch method: Launch agents via SSH, nhập host, cổng 22, credentials (SSH key hoặc user/pass).
  5. Lưu lại — controller tự SSH vào, copy agent.jar và khởi động agent.
Node config (Groovy CasC ví dụ)jenkins:
  nodes:
    - permanent:
        name: "agent-linux-01"
        remoteFS: "/home/jenkins/agent"
        labelString: "linux docker"
        launcher:
          ssh:
            host: "10.0.1.20"
            port: 22
            credentialsId: "ssh-agent-key"

Agent JNLP / Inbound (WebSocket)

Với agent JNLP (nay gọi là inbound agent), chiều kết nối ngược lại: agent chủ động kết nối ra controller (hữu ích khi agent nằm sau NAT/firewall không cho phép controller SSH vào). Agent chạy file agent.jar tải từ controller.

terminal (trên máy agent)# Tải agent.jar từ chính controller
curl -sO https://jenkins.example.com/jnlpJars/agent.jar

# Kết nối bằng WebSocket (khuyến nghị — chỉ cần cổng 443/80)
java -jar agent.jar -url https://jenkins.example.com/ \
  -secret @secret-file.txt -name "agent-linux-01" \
  -webSocket -workDir "/home/jenkins/agent"
Kiểu launchAi chủ động kết nốiYêu cầu mạng
SSH agentController → AgentController cần SSH (22) tới agent
JNLP/Inbound (TCP)Agent → ControllerCần mở cổng TCP riêng cho inbound agent trên controller
JNLP/Inbound (WebSocket)Agent → ControllerChỉ cần cổng HTTP/HTTPS chuẩn (80/443) — đơn giản nhất qua firewall
🤔 Khi nào chọn JNLP/WebSocket thay vì SSH?Khi agent ở mạng cô lập, sau NAT, hoặc trong môi trường không cho phép controller khởi tạo kết nối vào (agent tự "gọi về"). Chế độ WebSocket đặc biệt tiện vì không cần mở thêm cổng TCP riêng — dùng luôn cổng HTTPS mà Jenkins UI đã chạy.

Giới hạn job theo label

Jenkinsfilepipeline {
  agent { label 'agent-linux-01' }  // ép job chạy đúng 1 agent cụ thể
  stages { stage('Test') { steps { sh './run-tests.sh' } } }
}
⚠️ Bảo mật khóa bí mật của agentSecret của inbound agent (hiển thị khi tạo node) cho phép bất kỳ ai có nó kết nối làm agent giả mạo vào controller. Không commit secret vào Git, và thu hồi/khởi tạo lại nếu rò rỉ.
✍️ Thực hànhTạo 1 permanent agent bằng SSH tới một VM Linux, gắn label linux, sau đó viết một Jenkinsfile ép chạy đúng agent đó bằng label và xác nhận log build hiện đúng hostname của agent.

Lesson 7.2

SSH & JNLP/WebSocket Agents

🎯 GoalLearn to add a permanent SSH agent step-by-step, understand how a JNLP/inbound agent connects via agent.jar, firewall/port considerations, and how to restrict jobs to labels.

Adding an SSH agent — step by step

  1. Prepare a Linux/Windows machine with Java installed (a version compatible with the controller), create a dedicated user (e.g. jenkins) with access to the working directory.
  2. On the controller: Manage Jenkins › Nodes › New Node, name it, choose "Permanent Agent".
  3. Fill in the Remote root directory (e.g. /home/jenkins/agent), attach Labels (e.g. linux docker).
  4. Choose Launch method: Launch agents via SSH, enter host, port 22, credentials (SSH key or user/pass).
  5. Save — the controller SSHes in, copies agent.jar, and starts the agent.
Node config (CasC example)jenkins:
  nodes:
    - permanent:
        name: "agent-linux-01"
        remoteFS: "/home/jenkins/agent"
        labelString: "linux docker"
        launcher:
          ssh:
            host: "10.0.1.20"
            port: 22
            credentialsId: "ssh-agent-key"

JNLP / Inbound (WebSocket) Agents

With a JNLP agent (now called an inbound agent), the connection direction is reversed: the agent initiates the connection out to the controller (useful when the agent sits behind NAT/firewall that won't let the controller SSH in). The agent runs the agent.jar file downloaded from the controller.

terminal (on the agent machine)# Download agent.jar from the controller itself
curl -sO https://jenkins.example.com/jnlpJars/agent.jar

# Connect using WebSocket (recommended — only needs port 443/80)
java -jar agent.jar -url https://jenkins.example.com/ \
  -secret @secret-file.txt -name "agent-linux-01" \
  -webSocket -workDir "/home/jenkins/agent"
Launch typeWho initiatesNetwork requirement
SSH agentController → AgentController needs SSH (22) to the agent
JNLP/Inbound (TCP)Agent → ControllerNeeds a dedicated open TCP port for inbound agents on the controller
JNLP/Inbound (WebSocket)Agent → ControllerOnly needs the standard HTTP/HTTPS port (80/443) — simplest through firewalls
🤔 When to pick JNLP/WebSocket over SSH?When the agent is on an isolated network, behind NAT, or in an environment that doesn't allow the controller to initiate inbound connections (the agent "calls home" instead). WebSocket mode is especially convenient since it needs no extra TCP port — it reuses the HTTPS port the Jenkins UI already runs on.

Restricting jobs to labels

Jenkinsfilepipeline {
  agent { label 'agent-linux-01' }  // force the job onto one specific agent
  stages { stage('Test') { steps { sh './run-tests.sh' } } }
}
⚠️ Protect the agent secretAn inbound agent's secret (shown when creating the node) lets anyone who has it connect a rogue agent to the controller. Never commit it to Git, and rotate it if leaked.

Bài 7.3

Docker Agent trong Pipeline

🎯 Mục tiêuDùng agent { docker {...} } và agent { dockerfile true } để chạy build trong container hermetic, tái lập được, không phụ thuộc môi trường agent vật lý.

Cần Docker Pipeline plugin

Plugin Docker Pipeline (cùng Docker Engine cài trên agent) cho phép Jenkinsfile khai báo image làm môi trường build ngay trong agent mà không cần cài Node.js/Python/... trực tiếp trên agent host.

agent { docker { image ... } }

Jenkinsfilepipeline {
  agent {
    docker {
      image 'node:18'
      label 'docker'            // chạy trên agent host có Docker
      args  '-v $HOME/.npm:/root/.npm' // mount cache npm
    }
  }
  stages {
    stage('Install & Test') {
      steps {
        sh 'npm ci'
        sh 'npm test'
      }
    }
  }
}

Jenkins tự động: kéo image, khởi động container, mount workspace agent host vào container tại cùng đường dẫn, chạy các sh step bên trong container, rồi dọn container sau khi build xong.

agent { dockerfile true }

Khi cần môi trường tùy biến hơn (nhiều tool, phiên bản đặc thù), thay vì dùng image có sẵn, dùng chính Dockerfile trong repo để build image tạm rồi chạy trong đó.

Jenkinsfilepipeline {
  agent {
    dockerfile {
      filename 'Dockerfile.ci'
      dir 'build'
      additionalBuildArgs '--build-arg VERSION=1.2'
    }
  }
  stages {
    stage('Build') { steps { sh 'make' } }
  }
}
build/Dockerfile.ciFROM ubuntu:22.04
RUN apt-get update && apt-get install -y make gcc
ARG VERSION
ENV APP_VERSION=$VERSION
CáchKhi dùngƯu điểm
docker { image '...' }Đã có image chuẩn public/nội bộNhanh, đơn giản, cache tốt
dockerfile trueCần tool/cấu hình đặc thù không có image sẵnToàn quyền kiểm soát môi trường, versioned cùng repo
🤔 Vì sao dùng Docker agent thay vì agent vật lý cài sẵn tool?Môi trường build trở nên hermetic (đóng gói, tái lập được) — không còn "chạy được trên máy tôi nhưng lỗi trên CI" vì mọi phiên bản tool đều cố định trong image. Nhiều job với yêu cầu Node/Python/Java khác nhau có thể dùng chung 1 agent host mà không xung đột.
⚠️ Docker-in-Docker & quyền truy cập socketAgent host cần cài Docker Engine và user Jenkins agent cần quyền truy cập docker.sock — đây là bề mặt tấn công cần cân nhắc (container có thể "thoát" ra host qua socket). Cân nhắc dùng agent chuyên dụng chỉ chạy Docker builds, tách biệt khỏi agent khác.
✍️ Thực hànhViết một Jenkinsfile dùng agent { docker { image 'python:3.12' } } để chạy pytest, sau đó đổi sang dockerfile true với một Dockerfile cài thêm 1 hệ thống lib mà image gốc không có.

Docker Agents in Pipeline

🎯 GoalUse agent { docker {...} } and agent { dockerfile true } to run builds in a hermetic, reproducible container, independent of the physical agent host environment.

Requires the Docker Pipeline plugin

The Docker Pipeline plugin (along with Docker Engine installed on the agent) lets a Jenkinsfile declare a build environment image right in agent, without installing Node.js/Python/... directly on the agent host.

agent { docker { image ... } }

Jenkinsfilepipeline {
  agent {
    docker {
      image 'node:18'
      label 'docker'            // runs on an agent host that has Docker
      args  '-v $HOME/.npm:/root/.npm' // mount npm cache
    }
  }
  stages {
    stage('Install & Test') {
      steps {
        sh 'npm ci'
        sh 'npm test'
      }
    }
  }
}

Jenkins automatically pulls the image, starts the container, mounts the agent host's workspace into the container at the same path, runs sh steps inside the container, then cleans up the container after the build.

agent { dockerfile true }

When you need a more customized environment (multiple tools, specific versions) instead of an off-the-shelf image, use the repo's own Dockerfile to build a throwaway image and run in it.

Jenkinsfilepipeline {

      filename 'Dockerfile.ci'
      dir 'build'
      additionalBuildArgs '--build-arg VERSION=1.2'
    }
  }
  stages {
    stage('Build') { steps { sh 'make' } }
  }
}

Kubernetes Plugin

🎯 GoalUnderstand how the Kubernetes plugin creates ephemeral agent pods on demand, use podTemplate/the kubernetes { yaml ... } block in a Jenkinsfile, the container-per-stage pattern, and the benefits of elastic scaling.

What is an ephemeral agent pod?

Instead of maintaining fixed agent VMs, the Kubernetes plugin lets the controller connect to a K8s cluster: whenever a build needs to run, the plugin creates a new Pod as the agent, and once the build finishes the Pod is deleted. No idle resource cost, and it scales automatically as load increases.

Using the kubernetes { yaml ... } block

Jenkinsfilepipeline {
  agent {
    kubernetes {
      yaml '''
        apiVersion: v1
        kind: Pod
        spec:
          containers:
          - name: maven
            image: maven:3.9-eclipse-temurin-17
            command: ["sleep"]
            args: ["99d"]
          - name: node
            image: node:18
            command: ["sleep"]
            args: ["99d"]
      '''
    }
  }
  stages {
    stage('Build backend') {
      steps { container('maven') { sh 'mvn -B clean package' } }
    }
    stage('Build frontend') {
      steps { container('node') { sh 'npm ci && npm run build' } }
    }
  }
}

Container-per-stage

An agent Pod can hold multiple containers — each one a distinct tool environment (Maven, Node, kubectl...) sharing the Pod's workspace (volume). The container('name') step tells the next sh/bat command which container to run in.

🎯 GoalUnderstand the cloud agent concept (EC2 plugin, Azure VM Agents) — auto-provisioning VMs on demand, idle timeout, cost considerations, and using spot/preemptible instances.

What is a cloud agent?

Unlike static (SSH) agents or ephemeral K8s agents, a "Cloud" in Jenkins is an abstract configuration that declares how to automatically create VM agents on a cloud platform (AWS, Azure, GCP...) when the build queue needs more capacity, and auto-terminate the VM once idle or work is done.

EC2 plugin (conceptual example)

Manage Jenkins › Clouds › Amazon EC2# Main settings:
Region: ap-southeast-1
AMI: ami-0abcd1234            # image pre-loaded with Java + agent.jar
Instance Type: t3.large

Idle termination time: 15     # minutes — terminate VM if idle too long
Labels: aws-linux
Jenkinsfilepipeline {
  agent { label 'aws-linux' }  // EC2 plugin auto-provisions a VM when needed
  stages { stage('Build') { steps { sh './build.sh' } } }
}

Azure VM Agents (conceptual example)

Similar to the EC2 plugin but using Azure Resource Manager: declare an image (Managed Image/Marketplace), VM size, and a pool with a max instance count. Jenkins calls the Azure API to create the VM, install the agent, run the build, then delete or deallocate the VM.

FactorMeaningGuidance
Idle timeoutTime a VM sits idle before being terminatedShort → saves cost; long → the next build starts faster (VM reuse)
Instance capMax VMs that can be created concurrentlyCaps runaway cost during a build spike
Spot/preemptible instanceCheaper VM that can be reclaimed at any timeGood for non-SLA-critical builds (parallel tests, feature branch builds)
Standardized AMI/imageImage with Java/agent.jar/tools pre-installedReduces VM startup time before the agent is ready to accept a job
🤔 Why use cloud agents instead of fixed 24/7 agents?Most teams don't build around the clock — keeping a fixed agent running 24/7 wastes money during idle time. Cloud agents provision exactly when there's demand and auto-terminate when idle, optimizing both cost and the ability to absorb sudden traffic spikes.
⚠️ Spot instance risk & startup timeSpot/preemptible instances can be reclaimed mid-build, causing failures — don't use them for critical release pipelines. Also, cloud VMs take longer to start (boot + install agent) than a K8s pod, so for workloads needing very fast turnaround, K8s ephemeral agents are usually a better fit.
