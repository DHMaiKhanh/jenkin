Getting Started

Mục tiêu giai đoạn: cài đặt được Jenkins, đi qua trình cài đặt ban đầu, làm quen giao diện, tạo Pipeline đầu tiên và biết chạy Jenkins bằng Docker.Stage goal: install Jenkins, get through the initial setup wizard, learn the UI, create your first Pipeline, and know how to run Jenkins with Docker.

Bài 1.1

Cài đặt Jenkins

🎯 Mục tiêuBiết các cách cài Jenkins chính thức (WAR file, Docker, gói hệ điều hành), hiểu yêu cầu hệ thống tối thiểu, và biết JENKINS_HOME chứa gì.

Yêu cầu hệ thống

Theo tài liệu chính thức, Jenkins cần Java 11 hoặc 17 (tùy phiên bản LTS), tối thiểu 256MB RAM cho Jenkins (khuyến nghị ≥ 4GB cho môi trường thật), và ít nhất 10GB dung lượng đĩa cho JENKINS_HOME.

terminal# Kiểm tra phiên bản Java trước khi cài
java -version

Cách 1 — Chạy trực tiếp file WAR

Đây là cách cài đặt "chuẩn" nhất, chạy được trên mọi hệ điều hành có Java: tải jenkins.war từ jenkins.io rồi chạy bằng lệnh java -jar.

terminal# Tải bản LTS mới nhất
curl -fsSL https://get.jenkins.io/war-stable/latest/jenkins.war -o jenkins.war

# Chạy Jenkins, mặc định lắng nghe cổng 8080
java -jar jenkins.war
⚠️ Trên Windows (PowerShell)curl trong PowerShell chỉ là alias của Invoke-WebRequest và không hiểu các cờ kiểu Linux như -fsSL. Dùng curl.exe (ép gọi đúng binary curl thật) hoặc lệnh gốc Invoke-WebRequest: 
PowerShell# Cách 1 — gọi đúng curl.exe
curl.exe -fsSL https://get.jenkins.io/war-stable/latest/jenkins.war -o jenkins.war

# Cách 2 — dùng lệnh PowerShell gốc
Invoke-WebRequest -Uri "https://get.jenkins.io/war-stable/latest/jenkins.war" -OutFile "jenkins.war"

Chạy Jenkins trên cổng khác

Mặc định Jenkins lắng nghe cổng 8080. Muốn đổi sang cổng khác (ví dụ khi 8080 đã bị chiếm), dùng tham số --httpPort — cú pháp giống nhau trên mọi hệ điều hành:

terminal# Chạy Jenkins trên cổng 9090 thay vì 8080
java -jar jenkins.war --httpPort=9090

Sau khi chạy, truy cập http://localhost:9090 (theo đúng cổng vừa đặt).

💡 Vài tham số cổng hữu ích

--httpPort=-1 — tắt hẳn cổng HTTP, thường dùng khi bật HTTPS.

--httpsPort=8443 — bật HTTPS ở cổng 8443. Kết hợp cả hai để chỉ chạy HTTPS: java -jar jenkins.war --httpPort=-1 --httpsPort=8443.

Xem toàn bộ tham số hỗ trợ bằng java -jar jenkins.war --help.

Sau khi chạy, Jenkins sẽ tự tạo thư mục JENKINS_HOME (mặc định ~/.jenkins trên Linux/macOS, %USERPROFILE%\.jenkins trên Windows) để lưu toàn bộ cấu hình, job, plugin.

JENKINS_HOME~/.jenkins/
├── config.xml              # cấu hình toàn cục
├── secrets/
│   └── initialAdminPassword # mật khẩu admin lần đầu
├── jobs/                    # mỗi job/pipeline một thư mục con
├── plugins/                 # các plugin đã cài (.jpi/.hpi)
├── workspace/                # nơi checkout code & chạy build
└── users/                    # tài khoản người dùng

Cách 2 — Docker

terminaldocker run -p 8080:8080 -p 50000:50000 -v jenkins_home:/var/jenkins_home jenkins/jenkins:lts

Cách 3 — Gói cài đặt hệ điều hành (apt/yum)

terminal (Debian/Ubuntu)# Thêm key + repo chính thức của Jenkins
sudo wget -O /usr/share/keyrings/jenkins-keyring.asc https://pkg.jenkins.io/debian-stable/jenkins.io-2023.key
echo deb [signed-by=/usr/share/keyrings/jenkins-keyring.asc] https://pkg.jenkins.io/debian-stable binary/ | sudo tee /etc/apt/sources.list.d/jenkins.list

sudo apt-get update

sudo yum install jenkins

Lesson 1.1

Installing Jenkins

🎯 GoalKnow the official ways to install Jenkins (WAR file, Docker, OS packages), understand the minimum system requirements, and know what JENKINS_HOME contains.

System requirements

Per the official docs, Jenkins requires Java 11 or 17 (depending on the LTS release), at least 256MB RAM (≥ 4GB recommended for real usage), and at least 10GB of disk space for JENKINS_HOME.

terminal# Check the Java version before installing
java -version

Option 1 — Run the WAR file directly

This is the most "standard" installation method, running on any OS with Java: download jenkins.war from jenkins.io and run it with java -jar.

terminal# Download the latest LTS release
curl -fsSL https://get.jenkins.io/war-stable/latest/jenkins.war -o jenkins.war

# Run Jenkins, listens on port 8080 by default
java -jar jenkins.war
⚠️ On Windows (PowerShell)curl in PowerShell is just an alias for Invoke-WebRequest and doesn't understand Linux-style flags like -fsSL. Use curl.exe (forces the real curl binary) or the native Invoke-WebRequest cmdlet: 
PowerShell# Option 1 — call the real curl.exe
curl.exe -fsSL https://get.jenkins.io/war-stable/latest/jenkins.war -o jenkins.war

# Option 2 — use the native PowerShell cmdlet
Invoke-WebRequest -Uri "https://get.jenkins.io/war-stable/latest/jenkins.war" -OutFile "jenkins.war"

Running on a different port

By default Jenkins listens on port 8080. To switch to another port (e.g. when 8080 is already taken), use the --httpPort flag — the syntax is the same on every OS:

terminal# Run Jenkins on port 9090 instead of 8080
java -jar jenkins.war --httpPort=9090

Once it's running, visit http://localhost:9090 (using whichever port you set).

💡 Handy port flags

--httpPort=-1 — disables the HTTP port entirely, typically used when enabling HTTPS.

--httpsPort=8443 — enables HTTPS on port 8443. Combine both to run HTTPS only: java -jar jenkins.war --httpPort=-1 --httpsPort=8443.

See all supported parameters with java -jar jenkins.war --help.

Once running, Jenkins automatically creates a JENKINS_HOME directory (default ~/.jenkins on Linux/macOS, %USERPROFILE%\.jenkins on Windows) to store all configuration, jobs, and plugins.

JENKINS_HOME~/.jenkins/
├── config.xml              # global configuration
├── secrets/
│   └── initialAdminPassword # first-run admin password
├── jobs/                    # one subfolder per job/pipeline
├── plugins/                 # installed plugins (.jpi/.hpi)
├── workspace/                # where source is checked out & builds run
└── users/                    # user accounts

🤔 Why does Jenkins default to port 8080?8080 is a common "alternate" HTTP port that doesn't require root/admin privileges to bind (unlike port 80). You can change it with --httpPort=9090 or the JENKINS_PORT environment variable.
⚠️ Common mistakeInstalling Jenkins via apt/yum but not knowing JENKINS_HOME lives at /var/lib/jenkins (different from the manual WAR run's ~/.jenkins) — leading to looking in the wrong place when backing up or debugging.
⚠️ "Address already in use" error — port 8080 is takenIf running java -jar jenkins.war throws java.net.BindException: Address already in use: bind → Failed to bind to 0.0.0.0/0.0.0.0:8080, it means port 8080 is already used by another process — most likely another Jenkins that's still running from before. Three ways to fix it:

Option 1 — Use the Jenkins that's already running: Jenkins may already be up. Open http://localhost:8080 in your browser; if it loads, you don't need to restart it.

Option 2 — Find and kill the process holding port 8080:

PowerShell# See which process is holding port 8080
Get-Process -Id (Get-NetTCPConnection -LocalPort 8080).OwningProcess

# If it's java (old Jenkins), kill it, then run java -jar jenkins.war again
Stop-Process -Id (Get-NetTCPConnection -LocalPort 8080).OwningProcess -Force

Option 3 — Run Jenkins on a different port (if port 8080 is used by another app you want to keep):

terminaljava -jar jenkins.war --httpPort=9090
Then visit http://localhost:9090.

Trình cài đặt ban đầu (Setup Wizard)

🎯 Mục tiêuHiểu quy trình mở khóa Jenkins lần đầu, sự khác nhau giữa "Install suggested plugins" và chọn plugin thủ công, và tạo được tài khoản admin đầu tiên.

Bước 1 — Mở khóa Jenkins (Unlock Jenkins)

Lesson 1.2

Post-Installation Setup Wizard

🎯 GoalUnderstand the process of unlocking Jenkins the first time, the difference between "Install suggested plugins" and selecting plugins manually, and how to create the first admin account.

Step 1 — Unlock Jenkins

The first time you visit http://localhost:8080, Jenkins asks you to paste the initial admin password to confirm you have access to the server. This password is auto-generated and written to a file.

terminal# Linux/macOS — manual WAR run
cat ~/.jenkins/secrets/initialAdminPassword

# Installed via apt/yum
sudo cat /var/lib/jenkins/secrets/initialAdminPassword

# Docker container
docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword

Step 2 — Install plugins

After unlocking, Jenkins offers two choices for installing plugins:

ChoiceContentWhen to pick it
Install suggested pluginsThe most common plugin set: Git, Pipeline, GitHub, Credentials Binding, Matrix Auth...Beginners who want a Jenkins that immediately works for most use cases
Select plugins to installFull list, tick exactly the plugins you needProduction environments that need a minimal footprint and tight attack surface
💡 You can install more plugins laterWhichever option you pick here, you can always go to Manage Jenkins → Plugins to install or remove plugins at any time afterward.

Step 3 — Create the first admin user

The form asks for a username, password, full name, and email. This becomes the first full-access admin account, replacing the need to keep using the initialAdminPassword.

sample formUsername:  admin
Password:  ********
Full name: DevOps Admin
E-mail:    admin@example.com

The final step confirms the Jenkins URL (the address Jenkins uses to reference itself, e.g. in build notification emails), then click "Start using Jenkins".

🤔 Why require pasting a password file instead of just asking?Requiring you to read a file on the server itself proves you have filesystem/console access to that machine — preventing a stranger on the network from claiming admin rights on a freshly installed, still-unprotected Jenkins.
⚠️ Common mistakeClicking "Skip and continue as admin" in a non-demo environment — Jenkins keeps using the default admin account with a random password, causing trouble logging in later.
✍️ ExerciseStarting fresh, install Jenkins via Docker, retrieve the password with docker exec, choose "Install suggested plugins", then create an admin account with your own name instead of clicking "Skip".

Vì sao chạy Docker chung với Jenkins? — 2 mục đích

Nhiều người hay nhầm lẫn: "Docker + Jenkins" thực ra phục vụ hai mục đích hoàn toàn khác nhau. Nên phân biệt rõ hai kiểu này trước khi đi vào lệnh cụ thể.

1 · Chạy Jenkins bên trong Docker (Jenkins-in-Docker)

  • Cài đặt nhanh, không làm bẩn máy — không cần cài Java hay cài trực tiếp lên hệ điều hành; xóa container là sạch.
  • Dễ nâng cấp / rollback — chỉ cần đổi tag image (ví dụ từ lts sang phiên bản mới).
  • Tái lập môi trường giống hệt trên máy dev, server, hay CI khác nhau.
  • Dữ liệu Jenkins (job, config, plugin) lưu ở volume jenkins_home nên không mất khi container bị xóa.

2 · Jenkins dùng Docker để build/test (Docker-in-Pipeline)

Đây mới là lý do chính khiến Docker + Jenkins mạnh. Trong pipeline, mỗi bước build chạy trong một container riêng, mới tinh:

Jenkinsfilepipeline {
    agent {
        docker { image 'node:20' }   // build trong container Node 20 sạch
    }
    stages {
        stage('Build') {
            steps { sh 'npm install && npm run build' }
        }
    }
}
  • Môi trường build sạch & nhất quán — mỗi lần build có môi trường mới tinh, tránh cảnh "máy tôi chạy được mà server thì lỗi".
  • Không cần cài đủ thứ lên Jenkins server — cần Node 20 thì kéo image node:20, cần Python thì python:3.12, không xung đột phiên bản.
  • Cô lập — build project A không ảnh hưởng project B.
  • Đóng gói sản phẩm thành Docker image để deploy: build xong → tạo image → push lên registry → deploy lên server/K8s.
💡 Thực tế thường kết hợp cả haiJenkins chạy trong Docker, và pipeline của nó lại dùng Docker để build → tạo ra image để deploy. Phần còn lại của bài này đi sâu vào kiểu 1 (chạy Jenkins bằng Docker); kiểu 2 (pipeline dùng Docker) được nói kỹ hơn ở mục "Docker-in-Docker" cuối bài.

Lesson 1.5

Running Jenkins with Docker

🎯 GoalRun Jenkins with docker run using the correct ports and volume, write an equivalent docker-compose.yml, understand why persisting JENKINS_HOME matters, and know the Docker-in-Docker concept for pipelines that build images.

Why run Docker with Jenkins? — 2 purposes

People often mix this up: "Docker + Jenkins" actually serves two completely different purposes. It helps to tell them apart before diving into specific commands.

ModeWhat it meansMain benefit
Jenkins inside DockerJenkins itself runs as a containerQuick install, easy upgrades, clean host
Jenkins using DockerPipeline builds/tests inside their own containerClean, consistent environment, easy deploy

1 · Running Jenkins inside Docker (Jenkins-in-Docker)

This means Jenkins itself is installed as a container — exactly what the docker run / docker-compose commands below do.

  • Fast install, no mess on the host — no need to install Java or anything directly on the OS; delete the container and it's gone clean.
  • Easy upgrade / rollback — just change the image tag (e.g. from lts to a newer version).
  • Reproducible environment across dev machines, servers, and other CI setups.
  • Jenkins data (jobs, config, plugins) lives in the jenkins_home volume, so it survives container deletion.

2 · Jenkins using Docker to build/test (Docker-in-Pipeline)

This is the main reason Docker + Jenkins is so powerful. In a pipeline, each build step runs inside its own fresh container:

Jenkinsfilepipeline {
    agent {
        docker { image 'node:20' }   // build in a clean Node 20 container
    }
    stages {
        stage('Build') {
            steps { sh 'npm install && npm run build' }
        }
    }
}
  • Clean & consistent build environment — every build gets a brand-new environment, avoiding "works on my machine but fails on the server".
  • No need to install everything on the Jenkins server — need Node 20? pull node:20; need Python? python:3.12 — no version conflicts.
  • Isolation — building project A doesn't affect project B.
  • Packaging the product as a Docker image for deployment: build → create image → push to a registry → deploy to a server/K8s.
💡 In practice you usually combine bothJenkins runs inside Docker, and its pipeline in turn uses Docker to build → producing an image to deploy. The rest of this lesson focuses on mode 1 (running Jenkins via Docker); mode 2 (pipelines using Docker) is covered in more depth in the "Docker-in-Docker" section at the end.

Why persisting JENKINS_HOME matters

All of Jenkins' important data — jobs, build history, plugins, credentials, security configuration — lives under /var/jenkins_home inside the container. Without a mounted volume, deleting the container means losing everything.

⚠️ Common mistakeRunning docker run without -v jenkins_home:/var/jenkins_home — everything works fine until someone runs docker rm, at which point all jobs and build history are permanently gone.

Docker-in-Docker for pipelines that build images

If your Jenkinsfile needs to run docker build to package the app into an image, the Jenkins container (which is itself Docker) needs permission to run Docker inside it. The most common approach is to mount the host's Docker socket into the Jenkins container instead of running true Docker-in-Docker (DinD).

terminaldocker run -d \
  --name jenkins \
  -p 8080:8080 -p 50000:50000 \
  -v jenkins_home:/var/jenkins_home \
  -v /var/run/docker.sock:/var/run/docker.sock \
  jenkins/jenkins:lts
🤔 Why use the Docker socket instead of real Docker-in-Docker?Mounting the socket lets Jenkins "borrow" the host machine's Docker daemon, avoiding a nested Docker daemon running inside the container (complex, resource-heavy, requires --privileged). Trade-off: containers built by Jenkins are actually "siblings" running on the same host Docker daemon, not fully isolated from Jenkins.

1 · Pipeline

The modern, recommended job type. The whole build → test → deploy flow is described as code — a Jenkinsfile written in Declarative or Scripted (Groovy) syntax. Supports multiple stages, parallel execution (parallel), running across multiple agents, and survives Jenkins restarts. Because it's code, the pipeline is version-controlled alongside the app.

2 · Freestyle project

The classic job type, configured entirely through the web UI (point-and-click). Checks out from up to one SCM, runs build steps serially (shell, batch, Maven...), then post-build steps (archive artifacts, email...). Beginner-friendly, but limited: no visual stages/parallel, hard to version-control, hard to reuse once the workflow gets complex.

3 · Multi-configuration project (Matrix project)

Runs the same build configuration across many combinations (a matrix) — each dimension is an "axis". E.g. testing on 3 JDK versions × 2 operating systems = 6 automatic runs. Ideal for cross-platform, cross-version, cross-browser testing.

4 · Folder

Not a job — a "container" for grouping and organizing nested items. Unlike a View (just a display filter on the Dashboard), a Folder creates a separate namespace, so you can have two jobs with the same name as long as they live in different folders. Folders can also hold folder-scoped credentials/config.

5 · Multibranch Pipeline

Automatically creates a child Pipeline for each branch (and usually each Pull Request) containing a Jenkinsfile in one repo. Jenkins scans the repo: new branch → new job, deleted branch → job removed. Perfect for multi-branch Git workflows.

6 · Organization Folder

One level above Multibranch: it scans a whole organization/group (GitHub org, GitLab group, Bitbucket project) and automatically creates a Multibranch Pipeline per repo that has a Jenkinsfile. Great for large orgs with many repos — add a new repo and Jenkins picks it up and builds it on its own.

TypeWhat it isWhen to use
PipelineJob defined by a Jenkinsfile (code)Modern CI/CD — the default choice
Freestyle projectUI-configured job, runs steps seriallySimple few-step tasks, beginners
Multi-configurationJob run across a matrix of configsCross-platform / cross-version testing
FolderContainer that creates its own namespaceGrouping & organizing many jobs
Multibranch PipelineAuto-generates a pipeline per branch of 1 repoMulti-branch Git repo + Pull Requests
Organization FolderAuto-generates multibranch for every repo in an orgMany repos in one organization
🤔 What's the difference between a job and a container?The first 3 types (Pipeline, Freestyle, Multi-configuration) are real jobs that run builds. The last 3 (Folder, Multibranch, Organization Folder) are containers: they don't build anything themselves. In particular, Multibranch and Organization Folder go further and auto-create child jobs for you based on repo contents, instead of you creating each one by hand.
⚠️ Common mistakePicking Freestyle for a multi-step CI/CD flow, then getting stuck when you need stages/parallel or want the config in Git — forcing a rewrite as a Pipeline. Or confusing Multibranch Pipeline (one repo, many branches) with Organization Folder (many repos in one org).

    pick typePipeline

    pick typeMulti-configuration project

    pick typeFolder

    pick typeMultibranch Pipeline

    pick typeOrganization Folder
