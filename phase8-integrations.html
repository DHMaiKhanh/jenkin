Bài 8.1

Git/GitHub & Webhooks

🎯 Mục tiêuCấu hình Jenkins lấy code từ Git/GitHub, thiết lập webhook để build tự động khi có push, và biết cách bảo mật webhook.

Cấu hình Git plugin cho Freestyle/Pipeline

Plugin Git cung cấp bước SCM để checkout mã nguồn. Trong Pipeline, dùng bước checkout scm hoặc khai báo trực tiếp git.

Jenkinsfilepipeline {
  agent any
  stages {
    stage('Checkout') {
      steps {
        git branch: 'main',
            url: 'https://github.com/org/repo.git',
            credentialsId: 'github-creds'
      }
    }
  }
}

Webhook GitHub → Jenkins

Vào GitHub repo → Settings → Webhooks → Add webhook, Payload URL trỏ về http://<jenkins-host>/github-webhook/, Content type application/json, chọn sự kiện Push (và Pull request nếu cần). Trong job Jenkins, bật "GitHub hook trigger for GITScm polling" (plugin GitHub) hoặc dùng Multibranch Pipeline với GitHub Branch Source để tự động phát hiện branch/PR mà không cần cấu hình từng job.

CáchPluginKhi dùng
GitHub hook triggerGitHub pluginJob đơn, cần build khi push lên 1 repo cụ thể
GitHub Branch SourceGitHub Branch Source pluginMultibranch Pipeline — tự tạo job cho mỗi branch/PR
Poll SCMGit pluginKhông mở được webhook (mạng nội bộ), chấp nhận độ trễ
Jenkinsfile (multibranch)pipeline {
  agent any
  triggers {
    githubPush() // trigger khi nhận webhook push
  }
  stages {
    stage('Build') { steps { sh 'make build' } }
  }
}
🤔 Vì sao webhook tốt hơn polling?Poll SCM phải chạy định kỳ (VD mỗi phút) kiểm tra thay đổi → tốn tài nguyên và có độ trễ. Webhook đẩy sự kiện ngay khi push xảy ra → build gần như tức thời và không tốn chu kỳ CPU chờ đợi.
⚠️ Bảo mật webhook• Dùng HTTPS cho Jenkins URL nếu public.
• Cấu hình secret token trong webhook GitHub và xác thực bằng plugin (VD "Generic Webhook Trigger" hỗ trợ HMAC).
• Hạn chế IP nguồn (GitHub công bố dải IP webhook) bằng firewall/reverse proxy nếu Jenkins expose ra internet.
• Không để endpoint /github-webhook/ lộ thông tin nhạy cảm trong response.
✍️ Thực hànhTạo Multibranch Pipeline trỏ tới một repo GitHub thật, cấu hình GitHub Branch Source, thêm webhook, push một commit và quan sát Jenkins tự động phát hiện + build.

Lesson 8.1

Git/GitHub & Webhooks

🎯 GoalConfigure Jenkins to pull code from Git/GitHub, set up webhooks so builds trigger automatically on push, and know how to secure webhooks.

Configuring the Git plugin for Freestyle/Pipeline

The Git plugin provides the SCM step to check out source code. In Pipeline, use checkout scm or declare git directly.

Jenkinsfilepipeline {
  agent any
  stages {
    stage('Checkout') {
      steps {
        git branch: 'main',
            url: 'https://github.com/org/repo.git',
            credentialsId: 'github-creds'
      }
    }
  }
}

GitHub → Jenkins Webhook

In the GitHub repo go to Settings → Webhooks → Add webhook, set the Payload URL to http://<jenkins-host>/github-webhook/, Content type application/json, select the Push event (and Pull request if needed). In the Jenkins job, enable "GitHub hook trigger for GITScm polling" (GitHub plugin) or use a Multibranch Pipeline with the GitHub Branch Source to auto-discover branches/PRs without configuring each job.

ApproachPluginWhen to use
GitHub hook triggerGitHub pluginSingle job, build on push to one specific repo
GitHub Branch SourceGitHub Branch Source pluginMultibranch Pipeline — auto-creates jobs per branch/PR
Poll SCMGit pluginWebhook not reachable (internal network), latency acceptable
Jenkinsfile (multibranch)pipeline {
  agent any
  triggers {
    githubPush() // trigger on incoming push webhook
  }
  stages {
    stage('Build') { steps { sh 'make build' } }
  }
}
🤔 Why are webhooks better than polling?Poll SCM has to run periodically (e.g. every minute) checking for changes — wasting resources and adding latency. A webhook pushes the event the moment a push happens, so builds start almost instantly with no idle polling.
⚠️ Securing webhooks• Use HTTPS for the Jenkins URL if public.
• Configure a secret token on the GitHub webhook and verify it with a plugin (e.g. "Generic Webhook Trigger" supports HMAC).
• Restrict source IPs (GitHub publishes its webhook IP ranges) via firewall/reverse proxy if Jenkins is internet-facing.
• Don't let the /github-webhook/ endpoint leak sensitive info in responses.
✍️ ExerciseCreate a Multibranch Pipeline pointing at a real GitHub repo, configure GitHub Branch Source, add a webhook, push a commit, and watch Jenkins auto-discover and build it.

Blue Ocean

🎯 Mục tiêuCài đặt Blue Ocean, hiểu visual pipeline editor và khả năng trực quan hóa run, biết khi nào nên/không nên dùng.

Cài đặt

Vào Manage Jenkins → Plugins → Available, tìm và cài Blue Ocean (đây là một tập hợp plugin, cài chung sẽ kéo theo các plugin con). Sau khi cài, truy cập tại /blue trên URL Jenkins.

terminal (Jenkins CLI)jenkins-plugin-cli --plugins blueocean

Visual Pipeline Editor

Blue Ocean cho phép tạo/sửa Pipeline bằng kéo-thả các stage/step, sau đó xuất ra một Jenkinsfile chuẩn commit vào repo — không có "định dạng ẩn" riêng, editor chỉ sinh cú pháp Declarative Pipeline thông thường.

Trực quan hóa build

Màn hình run hiển thị các stage dạng sơ đồ ngang, log riêng từng bước, thời gian chạy mỗi stage, và view riêng cho Pull Request/branch trong Multibranch Pipeline.

Tiêu chíBlue OceanClassic UI
Trực quan hóa stageSơ đồ đẹp, dễ đọcBảng stage view cơ bản
Chỉnh sửa PipelineKéo-thả trực quanChỉnh Jenkinsfile trực tiếp
Tình trạng phát triểnBảo trì (maintenance mode) từ 2020, không thêm tính năng mớiĐang phát triển tích cực

🤔 Vì sao vẫn học Blue Ocean?Nhiều tổ chức vẫn dùng nó để xem trực quan pipeline phức tạp (parallel stage, matrix) dễ hơn nhiều so với classic UI, dù không còn phát triển thêm.
⚠️ Blue Ocean đang ở chế độ bảo trìTừ 2020 team Jenkins tuyên bố chỉ vá lỗi bảo mật, không phát triển tính năng mới. Nếu cần trải nghiệm hiện đại hơn, cân nhắc các giải pháp thay thế như giao diện Pipeline Stage View mới trong Jenkins core, hoặc các nền tảng CI khác có UI trực quan tích hợp sẵn.
✍️ Thực hànhCài Blue Ocean, mở một Multibranch Pipeline có sẵn, dùng editor tạo một stage mới bằng kéo-thả, xem Jenkinsfile được sinh ra và commit nó vào repo.

Lesson 8.2

Blue Ocean

🎯 GoalInstall Blue Ocean, understand the visual pipeline editor and run visualization, and know when to use it vs. the classic UI.

Installation

Go to Manage Jenkins → Plugins → Available, find and install Blue Ocean (it's a bundle of plugins — installing it pulls in the dependent ones). Once installed, access it at /blue on your Jenkins URL.

terminal (Jenkins CLI)jenkins-plugin-cli --plugins blueocean

Visual Pipeline Editor

Blue Ocean lets you create/edit a Pipeline by dragging and dropping stages/steps, then exports a standard Jenkinsfile to commit to your repo — there is no hidden proprietary format, the editor just generates plain Declarative Pipeline syntax.

Run Visualization

The run screen shows stages as a horizontal diagram, per-step logs, per-stage timing, and dedicated Pull Request/branch views for Multibranch Pipelines.

CriterionBlue OceanClassic UI
Stage visualizationClean, readable diagramBasic stage view table
Editing pipelinesVisual drag-and-dropEdit the Jenkinsfile directly
Development statusMaintenance mode since 2020, no new featuresActively developed
New plugin supportMany plugins lack Blue Ocean UI supportFull plugin support
🤔 Why still learn Blue Ocean?Many organizations still use it because visualizing complex pipelines (parallel stages, matrix) is much easier than the classic UI, even though it's no longer actively developed.
⚠️ Blue Ocean is in maintenance modeSince 2020 the Jenkins team has stated it only receives security fixes, no new features. For a more modern experience, consider alternatives like the newer Pipeline Stage View built into Jenkins core, or other CI platforms with built-in visual UIs.
✍️ ExerciseInstall Blue Ocean, open an existing Multibranch Pipeline, use the editor to add a new stage by drag-and-drop, inspect the generated Jenkinsfile, and commit it to the repo.

Bài 8.3

Thông báo (Notifications)

🎯 Mục tiêuCấu hình Email-ext gửi mail khi build thất bại, gửi thông báo Slack qua slackSend, và điều kiện hóa thông báo theo kết quả build.

Email-ext — cấu hình SMTP

Vào Manage Jenkins → System, mục Extended E-mail Notification: nhập SMTP server, port, bật SSL/TLS nếu cần, và thiết lập Default user e-mail suffix/credentials gửi mail.

Jenkinsfilepipeline {
  agent any
  stages {
    stage('Build') { steps { sh './build.sh' } }
  }
  post {
    failure {
      mail to: 'team@example.com',
           subject: "FAILED: ${env.JOB_NAME} #${env.BUILD_NUMBER}",
           body: "Xem chi tiết tại: ${env.BUILD_URL}"
    }
  }
}

Với Email-ext plugin có thể dùng bước nâng cao hơn emailext để đính kèm log, dùng template HTML:

Jenkinsfilepost {
  failure {
    emailext subject: '$DEFAULT_SUBJECT',
             body: '$DEFAULT_CONTENT',
             attachLog: true,
             to: 'team@example.com'
  }
}

Slack Notification — slackSend

Cài plugin Slack Notification, tạo Slack App/Webhook, cấu hình workspace token trong Manage Jenkins → System → Slack. Trong Jenkinsfile:

Jenkinsfilepost {
  success {
    slackSend channel: '#ci-cd',
              color: 'good',
              message: "✅ ${env.JOB_NAME} #${env.BUILD_NUMBER} thành công"
  }
  failure {
    slackSend channel: '#ci-cd',
              color: 'danger',
              message: "❌ ${env.JOB_NAME} #${env.BUILD_NUMBER} thất bại — ${env.BUILD_URL}"
  }
}
Điều kiện postKhi trigger
alwaysLuôn chạy bất kể kết quả
successBuild thành công
failureBuild thất bại
unstableBuild "không ổn định" (VD test fail nhưng không dừng build)
changedKết quả khác lần build trước (VD từ failure sang success)
🤔 Vì sao dùng changed thay vì gửi mọi lần?Gửi thông báo mỗi build gây "spam mệt mỏi" — team sẽ bỏ qua cảnh báo. Chỉ báo khi trạng thái thay đổi (fail→pass, pass→fail) giúp thông báo có ý nghĩa và được chú ý.
⚠️ Đừng để lộ thông tin nhạy cảmKhông đưa log đầy đủ hay biến môi trường bí mật vào nội dung thông báo Slack/email công khai. Dùng credentials() và mask output khi cần.
✍️ Thực hànhThêm khối post gửi Slack khi failure và email khi changed, thử làm 1 build fail rồi fix lại để thấy 2 loại thông báo khác nhau.
📚 5 ví dụ thực tế · Thông báo
  1. Gửi mail đơn giản khi build fail. 
    Jenkinsfilepost { failure { mail to: 'a@b.com', subject: 'Build failed', body: 'Xem Jenkins' } }
  2. Gửi Slack khi thành công. 
    Jenkinsfilepost { success { slackSend channel: '#ci', color: 'good', message: 'Build OK' } }
  3. Thông báo chỉ khi trạng thái thay đổi. 
    Jenkinsfilepost { changed { slackSend channel: '#ci', message: "Trạng thái đổi: ${currentBuild.currentResult}" } }
  4. Email đính kèm log build khi fail. 
    Jenkinsfilepost { failure { emailext attachLog: true, to: 'team@example.com', subject: '$DEFAULT_SUBJECT', body: '$DEFAULT_CONTENT' } }
  5. Thông báo unstable riêng biệt. 
    Jenkinsfilepost { unstable { slackSend channel: '#ci', color: 'warning', message: 'Build unstable — có test fail' } }

Lesson 8.3

Notifications

🎯 GoalConfigure Email-ext to send mail on build failure, send Slack notifications via slackSend, and condition notifications on the build result.

Email-ext — SMTP configuration

Go to Manage Jenkins → System, section Extended E-mail Notification: enter the SMTP server, port, enable SSL/TLS if needed, and set the Default user e-mail suffix/sending credentials.

Jenkinsfilepipeline {
  agent any
  stages {
    stage('Build') { steps { sh './build.sh' } }
  }
  post {
    failure {
      mail to: 'team@example.com',
           subject: "FAILED: ${env.JOB_NAME} #${env.BUILD_NUMBER}",
           body: "See details at: ${env.BUILD_URL}"
    }
  }
}

With the Email-ext plugin you can use the more advanced emailext step to attach logs and use an HTML template:

Jenkinsfilepost {
  failure {
    emailext subject: '$DEFAULT_SUBJECT',
             body: '$DEFAULT_CONTENT',
             attachLog: true,
             to: 'team@example.com'
  }
}

Slack Notification — slackSend

Install the Slack Notification plugin, create a Slack App/Webhook, configure the workspace token under Manage Jenkins → System → Slack. In a Jenkinsfile:

Jenkinsfilepost {
  success {
    slackSend channel: '#ci-cd',
              color: 'good',
              message: "✅ ${env.JOB_NAME} #${env.BUILD_NUMBER} succeeded"
  }
  failure {
    slackSend channel: '#ci-cd',
              color: 'danger',
              message: "❌ ${env.JOB_NAME} #${env.BUILD_NUMBER} failed — ${env.BUILD_URL}"
  }
}
post conditionTriggers when
alwaysAlways runs regardless of result
successBuild succeeded
failureBuild failed
unstableBuild is "unstable" (e.g. failed tests but build not aborted)
changedResult differs from the previous build (e.g. failure → success)
🤔 Why use changed instead of notifying every time?Notifying on every build causes "alert fatigue" — the team starts ignoring warnings. Only alerting on a status change (fail→pass, pass→fail) keeps notifications meaningful and noticed.
⚠️ Don't leak sensitive informationDon't put full logs or secret environment variables into public Slack/email notification bodies. Use credentials() and mask output where needed.
✍️ ExerciseAdd a post block that sends Slack on failure and email on changed; break a build and then fix it to see both types of notification fire.

The Copy Artifact plugin lets one job fetch archived artifacts from another job (even a different pipeline/repository):

JenkinsfilecopyArtifacts projectName: 'upstream-build',
             selector: lastSuccessful(),

MechanismScopeSurvives after the build ends?
stash/unstashWithin a single pipeline run, across agents/stagesNo — discarded at the end of the run
archiveArtifactsPersisted on the Jenkins controllerYes — subject to the discard-old-builds policy
Copy Artifact pluginBetween different jobsReads another job's already-archived artifacts

Jenkinsfileoptions {

}
🤔 How is stash different from archiveArtifacts?stash only lives temporarily for one pipeline run, moving files between different stages/agents; archiveArtifacts persists permanently on the controller for later download or review.
⚠️ Don't over-archiveArchiving large build outputs (e.g. an entire node_modules) on every build quickly fills the controller's disk. Only archive what's needed (binaries, reports) and always configure discard/retention.
