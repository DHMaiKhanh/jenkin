Security

Mục tiêu giai đoạn: hiểu và cấu hình đúng xác thực, phân quyền, quản lý credentials an toàn, và áp dụng các thực hành bảo mật được Jenkins khuyến nghị chính thức để bảo vệ controller và agent.Stage goal: correctly configure authentication and authorization, manage credentials securely, and apply Jenkins' officially recommended security practices to protect the controller and agents.

Bài 6.1

Authentication — Xác thực người dùng

🎯 Mục tiêuHiểu các "security realm" (nguồn xác thực) Jenkins hỗ trợ, cấu hình đúng cơ sở dữ liệu người dùng nội bộ, và biết cách vô hiệu hóa truy cập ẩn danh/đăng ký công khai.

Security Realm là gì?

Trong Manage Jenkins › Security, mục Security Realm quyết định Jenkins xác thực người dùng bằng cách nào — tức "bạn là ai".

Security RealmMô tảKhi nào dùng

LDAPỦy quyền xác thực cho máy chủ LDAP/Active DirectoryDoanh nghiệp đã có LDAP/AD
Unix user/group databaseDùng tài khoản hệ điều hành trên máy chủ JenkinsHiếm dùng, môi trường Unix đơn giản
SSO (plugin: SAML, OIDC, GitHub OAuth...)Ủy quyền cho nhà cung cấp danh tính bên ngoàiMuốn đăng nhập một lần (SSO) qua Okta/Azure AD/Google...

Bật cơ sở dữ liệu người dùng nội bộ

Ủy quyền xác thực cho LDAP / SSO

Với LDAP, Jenkins không lưu mật khẩu — mọi lần đăng nhập được chuyển tiếp tới máy chủ LDAP để xác thực, sau đó Jenkins ánh xạ nhóm LDAP sang vai trò nội bộ (kết hợp với Authorization ở bài 6.2).

  Root DN: dc=company,dc=com
  User search base: ou=people
  Group search base: ou=groups
📁 Jenkins CLI & API cũng cần xác thựcNgoài UI, các kênh khác (REST API, CLI, remoting) cũng dùng cùng cơ chế realm. Token API cá nhân (My Account › API Token) nên dùng thay mật khẩu khi gọi script/CLI.
🤔 Vì sao nên ủy quyền cho LDAP/SSO thay vì DB nội bộ?DB nội bộ nghĩa là mật khẩu người dùng nằm trong Jenkins — nếu Jenkins bị xâm nhập, mật khẩu (dù hash) có nguy cơ lộ. Ủy quyền cho LDAP/SSO giúp tập trung vòng đời tài khoản (khóa/xóa nhân viên nghỉ việc ở một nơi duy nhất) và tận dụng MFA đã có ở IdP.
💡 Luôn tạo admin trước khi khóa "sign up"Thứ tự an toàn: 1) Cài Jenkins → tạo user admin đầu tiên qua wizard → 2) Bật Authorization phù hợp → 3) Tắt "Allow users to sign up".

Lesson 6.1

Authentication — User Authentication

🎯 GoalUnderstand the "security realms" Jenkins supports, correctly configure the internal user database, and know how to disable anonymous access/public sign-up.

What is a Security Realm?

Under Manage Jenkins › Security, the Security Realm section decides how Jenkins authenticates users — i.e. "who you are".

Security RealmDescriptionWhen to use
Jenkins' own user databaseUsers stored directly in JenkinsSmall teams, demos, no shared identity system
LDAPDelegates authentication to an LDAP/Active Directory serverEnterprises already running LDAP/AD
Unix user/group databaseUses OS accounts on the Jenkins hostRare, simple Unix environments
SSO (plugin: SAML, OIDC, GitHub OAuth...)Delegates to an external identity providerSingle sign-on via Okta/Azure AD/Google...

Enabling the internal user database

Manage Jenkins › Security# Security Realm = "Jenkins' own user database"
# ☐ Allow users to sign up   ← UNCHECK after creating the first admin!
⚠️ "Allow users to sign up" is a backdoorWhen enabled, anyone who reaches the Jenkins URL can self-register and (if Authorization is loose) end up with full control. This is a common way public Jenkins instances get taken over. Always disable it after creating the admin.

Delegating authentication to LDAP / SSO

With LDAP, Jenkins doesn't store passwords — every login is forwarded to the LDAP server for verification, then Jenkins maps LDAP groups to internal roles (combined with Authorization from lesson 6.2).

Configure Global SecuritySecurity Realm: LDAP
  Server: ldaps://ldap.company.com:636
  Root DN: dc=company,dc=com
  User search base: ou=people
  Group search base: ou=groups
📁 The Jenkins CLI & API also need authenticationBesides the UI, other channels (REST API, CLI, remoting) use the same realm. A personal API token (My Account › API Token) should be used in place of a password for scripts/CLI.
🤔 Why delegate to LDAP/SSO instead of the internal DB?The internal DB means user passwords live inside Jenkins — if Jenkins is compromised, hashed passwords are at risk of exposure. Delegating to LDAP/SSO centralizes account lifecycle (lock/remove a departing employee in one place) and leverages MFA already enforced at the IdP.
💡 Always create the admin before locking "sign up"Safe order: 1) Install Jenkins → create the first admin via the setup wizard → 2) Enable proper Authorization → 3) Disable "Allow users to sign up".
✍️ ExerciseGo to Manage Jenkins › Security, confirm the Security Realm is "Jenkins' own user database", and verify "Allow users to sign up" is unchecked. Create a new user via Manage Users and log in with it.

Authorization — Phân quyền

🎯 Mục tiêuHiểu sự khác biệt giữa Matrix-based Security, Project-based Matrix Authorization và Role-Based Strategy plugin, và biết áp dụng nguyên tắc "quyền hạn tối thiểu" (least privilege).

Các chiến lược Authorization có sẵn

Chiến lượcPhạm viGhi chú
Anyone can do anythingToàn cụcKhông dùng ở production — chỉ để demo cục bộ
Logged-in users can do anythingToàn cụcVẫn quá lỏng, ai đăng nhập cũng có quyền admin
Matrix-based securityToàn cụcGán quyền chi tiết (Job/Build/Read...) cho từng user/nhóm ở cấp instance
Project-based Matrix AuthorizationToàn cục + theo từng jobCho phép override quyền riêng cho từng project
Role-Based Strategy (plugin)Global / Item(Project) / Agent rolesĐịnh nghĩa "vai trò" theo pattern regex rồi gán user vào vai trò — dễ quản lý ở quy mô lớn

🤔 Vì sao "authenticated" nên chỉ có Read/Build?Nhóm ảo authenticated gồm mọi user đăng nhập. Nếu gán quyền Admin cho nhóm này, mọi tài khoản mới tạo mặc định đều có toàn quyền — vi phạm nguyên tắc least privilege.

Role-Based Strategy Plugin

Plugin Role-based Authorization Strategy cho phép định nghĩa 3 loại vai trò: Global roles (áp dụng toàn instance), Item roles (áp dụng theo pattern tên job/folder), và Agent roles (quyền trên agent cụ thể).

Manage and Assign Roles# Manage Roles
Global roles:  readonly, developer, admin
Item roles:
  pattern: ^team-a-.*   → role: team-a-dev  (Job: Read, Build, Configure)
  pattern: ^team-b-.*   → role: team-b-dev  (Job: Read, Build, Configure)

# Assign Roles
User: alice  → team-a-dev
User: bob    → team-b-dev, readonly
💡 Dùng pattern folder để cách ly teamKết hợp Folders plugin + Item roles theo regex (vd ^team-a-.*) giúp mỗi team chỉ thấy/sửa job của chính mình mà không cần tạo controller riêng.
⚠️ Đừng quên quyền Overall/ReadThiếu quyền Overall/Read cho một nhóm nghĩa là họ không thể vào UI dù có quyền Job cụ thể — lỗi cấu hình rất phổ biến khi mới dùng Matrix/Role-Based.
✍️ Thực hànhCài plugin Role-based Authorization Strategy, tạo 2 global role (readonly, developer) và 1 item role theo pattern ^demo-.*, gán cho một user thử nghiệm rồi kiểm tra quyền qua UI.

Lesson 6.2

Authorization — Access Control

🎯 GoalUnderstand the differences between Matrix-based Security, Project-based Matrix Authorization, and the Role-Based Strategy plugin, and apply the principle of least privilege.

Available Authorization strategies

StrategyScopeNotes
Anyone can do anythingGlobalNever use in production — local demos only
Logged-in users can do anythingGlobalStill too permissive — any logged-in user gets admin power
Matrix-based securityGlobalFine-grained permissions (Job/Build/Read...) per user/group at instance level
Project-based Matrix AuthorizationGlobal + per jobLets each project override its own permissions
Role-Based Strategy (plugin)Global / Item(Project) / Agent rolesDefine "roles" via regex patterns, then assign users to roles — scales well

Matrix-based Security

Manage Jenkins › SecurityAuthorization: Matrix-based security
┌──────────────┬──────┬───────┬───────┬────────┐
│ User/Group   │ Read │ Build │ Cancel│ Admin  │
├──────────────┼──────┼───────┼───────┼────────┤
│ Anonymous    │  ☐   │  ☐    │  ☐    │  ☐     │
│ authenticated│  ☑   │  ☑    │  ☐    │  ☐     │
│ devops-team  │  ☑   │  ☑    │  ☑    │  ☐     │
│ admin        │  ☑   │  ☑    │  ☑    │  ☑     │
└──────────────┴──────┴───────┴───────┴────────┘
🤔 Why should "authenticated" only get Read/Build?The virtual authenticated group includes every logged-in user. Granting it Admin means every newly created account defaults to full control — violating least privilege.

Role-Based Strategy Plugin

The Role-based Authorization Strategy plugin defines 3 kinds of roles: Global roles (instance-wide), Item roles (matched against job/folder name patterns), and Agent roles (permissions on specific agents).

Manage and Assign Roles# Manage Roles
Global roles:  readonly, developer, admin
Item roles:
  pattern: ^team-a-.*   → role: team-a-dev  (Job: Read, Build, Configure)
  pattern: ^team-b-.*   → role: team-b-dev  (Job: Read, Build, Configure)

# Assign Roles
User: alice  → team-a-dev
User: bob    → team-b-dev, readonly
💡 Use folder patterns to isolate teamsCombining the Folders plugin with regex-based Item roles (e.g. ^team-a-.*) lets each team see/edit only its own jobs without needing a separate controller.
⚠️ Don't forget Overall/ReadMissing Overall/Read for a group means they can't even reach the UI, even with specific Job permissions — a very common misconfiguration for newcomers to Matrix/Role-Based security.
✍️ ExerciseInstall the Role-based Authorization Strategy plugin, create 2 global roles (readonly, developer) and 1 item role matching pattern ^demo-.*, assign it to a test user, and verify permissions through the UI.

Bài 6.3

Credentials nâng cao

🎯 Mục tiêuHiểu credential domains, phạm vi credentials theo folder, sử dụng đúng Credentials Binding plugin (withCredentials) trong Jenkinsfile, và tránh làm lộ secret ra console log.

Credential Domains & phạm vi lưu trữ

Mỗi credential thuộc một domain (mặc định "(global)") và một store — có thể là System (toàn instance) hoặc gắn với một Folder cụ thể (khi dùng Folders plugin).

StorePhạm vi khả dụngDùng khi nào
Jenkins (global)Mọi job trên toàn instanceCredential dùng chung, ít nhạy cảm
Folder-scopedChỉ job bên trong folder đóCách ly credential theo team/dự án — team A không thấy secret của team B
Domain (theo hostname)Chỉ áp dụng khi kết nối tới host khớp domainNhiều credential SSH/HTTP khác nhau cho nhiều host
🤔 Vì sao nên đặt credential trong Folder thay vì global?Credential global có thể bị bất kỳ job nào trên instance sử dụng (kể cả job của team khác), làm tăng phạm vi ảnh hưởng khi rò rỉ. Folder-scoped credential giới hạn "bán kính nổ" (blast radius) đúng theo ranh giới team/dự án.

Credentials Binding trong Jenkinsfile

Jenkinsfilepipeline {
  agent any
  stages {
    stage('Deploy') {
      steps {
        withCredentials([
          usernamePassword(credentialsId: 'docker-hub', usernameVariable: 'DOCKER_USER', passwordVariable: 'DOCKER_PASS'),
          string(credentialsId: 'deploy-token', variable: 'DEPLOY_TOKEN'),
          sshUserPrivateKey(credentialsId: 'deploy-ssh-key', keyFileVariable: 'SSH_KEY')
        ]) {
          sh 'echo $DOCKER_PASS | docker login -u $DOCKER_USER --password-stdin'
          sh 'curl -H "Authorization: Bearer $DEPLOY_TOKEN" https://api.example.com/deploy'
        }
      }
    }
  }
}

Bên trong khối withCredentials, Jenkins tự động mask (che) giá trị secret trong console output — mọi chuỗi trùng khớp giá trị credential đều bị thay bằng ****.

⚠️ Đừng vô tình in secret ra logMask chỉ hoạt động với giá trị y hệt chuỗi gốc. Nếu bạn encode/biến đổi secret (base64, nối chuỗi khác), giá trị đã biến đổi sẽ KHÔNG được mask và lộ ra console. Tránh echo $DOCKER_PASS trực tiếp, tránh set -x trong shell khi có biến secret, và không dùng sh(returnStdout: true) để trả secret ra output pipeline.

Ràng buộc credential type với domain

Manage Jenkins › CredentialsAdd domain: internal-git
  Hostname specification: git.internal.company.com
# Credential SSH key chỉ áp dụng khi Jenkins kết nối đúng host này

✍️ Thực hànhTạo một Folder mới, thêm 1 credential "username/password" chỉ trong folder đó, viết Jenkinsfile dùng withCredentials để login vào một service giả lập, và xác nhận console log hiển thị **** thay vì mật khẩu thật.

Advanced Credentials Management

🎯 GoalUnderstand credential domains, folder-scoped credentials, correct use of the Credentials Binding plugin (withCredentials) in a Jenkinsfile, and how to avoid leaking secrets into the console log.

Credential Domains & storage scope

Each credential belongs to a domain (default "(global)") and a store — either System (instance-wide) or attached to a specific Folder (with the Folders plugin).

StoreAvailable scopeWhen to use
Jenkins (global)Every job on the instanceShared, low-sensitivity credentials
Folder-scopedOnly jobs inside that folderIsolate credentials per team/project — team A can't see team B's secrets
Domain (by hostname)Only applies when connecting to a matching hostMultiple SSH/HTTP credentials for different hosts
🤔 Why put credentials in a Folder instead of global?A global credential can be used by any job on the instance (including other teams' jobs), widening the blast radius if leaked. Folder-scoped credentials contain the blast radius to the team/project boundary.

Credentials Binding in a Jenkinsfile

Jenkinsfilepipeline {
  agent any
  stages {
    stage('Deploy') {
      steps {
        withCredentials([
          usernamePassword(credentialsId: 'docker-hub', usernameVariable: 'DOCKER_USER', passwordVariable: 'DOCKER_PASS'),
          string(credentialsId: 'deploy-token', variable: 'DEPLOY_TOKEN'),
          sshUserPrivateKey(credentialsId: 'deploy-ssh-key', keyFileVariable: 'SSH_KEY')
        ]) {
          sh 'echo $DOCKER_PASS | docker login -u $DOCKER_USER --password-stdin'
          sh 'curl -H "Authorization: Bearer $DEPLOY_TOKEN" https://api.example.com/deploy'
        }
      }
    }
  }
}

Inside a withCredentials block, Jenkins automatically masks secret values in console output — any string matching a bound credential value is replaced with ****.

⚠️ Don't accidentally print secrets to the logMasking only works on values identical to the original string. If you encode/transform a secret (base64, string concatenation), the transformed value will NOT be masked and can leak into the console. Avoid direct echo $DOCKER_PASS, avoid set -x in shell steps that touch secret variables, and don't use sh(returnStdout: true) to surface a secret in pipeline output.

  2. Why set the Built-In Node's executor count to 0?
    Answer
    // Forces all builds onto isolated agents instead of the controller — reduces risk from untrusted code affecting the whole system
  3. What does Agent → Controller Access Control protect against?
    Answer
    // Prevents a (potentially compromised) agent from sending sensitive commands to freely read/write on the controller
  4. Write a Jenkinsfile snippet pinning the agent to label "windows".

  5. Why forward audit logs to a centralized logging system (ELK/Splunk)?
